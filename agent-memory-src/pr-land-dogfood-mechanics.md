Landing WE work via `scripts/pr-land.mjs` (self-approved PR + `test` CI gate) — the non-obvious bits, learned dogfooding the #2162 drain slices (2026-07-02):

- **`--body-file` is effectively required.** A bodyless `gh pr create --title …` on a remote-only `lane/*` head drops into an interactive body prompt that **fails headless** (there is no `--fill` for a lane ref) → pr-land reports `gh-error` "gh pr create failed". Compose a body (change summary + the #2170 review dismissals via `lane-review body`) and pass `--body-file`. First #2173 attempt failed on exactly this.
- **`--park=<review:human|review:pending>` is the ONLY unconditional hold (2026-08-05).** `--park` (#2622) applies the review label **at open**, before any wait, keeping the same numbering / land-prep — so the old `gh pr create` park workaround is obsolete. Two flags read like a hold and are not. (a) `--no-wait` opens the PR *unlabelled*, and unlabelled is not held: `shouldLabelOnGreen` (#2216, `we:scripts/merge-ai-prs.mjs`) labels **any producer-owned AI PR** `ready-to-merge` once its required check reads green, remembering no earlier red run — so a re-run or a rebase that flips CI green labels it too, and the resident daemon ([[drain-is-a-resident-daemon]]) runs that reconcile continuously. (b) `--label=review:human` does hold once applied (#2820) — but `--label=<name>` only renames the label applied **inside the green path**, so on a red gate or a check-timeout it never fires and nothing holds the PR.
- **What `--no-wait` actually costs (measured on PR #1047, 2026-08-05): ~2 poll periods, not a hold.** The daemon labelled `ready-to-merge` **2m03s after `test` went green** — not the instant it went green. The label→merge leg (~6.4 min) is the drain's normal latency, which `--no-wait` does not change at all. Read check times on the head CI actually ran on: a drain rebase force-pushes a new head, and a check-runs read on the *current* head reports a misleadingly later time. (Full timeline + shas: the PR #1050 body.) The whole run is one PAT, so the label reads as the human's login — never an independence signal (#2439).
- **Which park value: `review:human` when the diff is genuinely gate-self, else `review:pending`.** Since #2895 landed, `review:human` HAS a clearance tool — `review-set-label.mjs --to=clear-human`, the only target that removes the label, requiring `--actor` and a `--reason` that quotes the operator's instruction. `decideSetLabel` still refuses `--to=accepted` on a `review:human` PR unconditionally (INVARIANT 2). Nothing verifies that a *human* ran `clear-human`; #2895 ruled that signal deferred (#2946 is the durable fix), so the tier is held by the rule in `we:skills-src/review/SKILL.md` — run it only on an explicit in-conversation operator instruction naming that PR. So do NOT downgrade a gate-self diff to `review:pending` for convenience. `review:pending` is the one an independent review can clear — but its non-author independence is a **norm you honour, not a predicate that runs**. Full statement of both values (and why): `we:skills-src/pr/SKILL.md`, the `--park` bullet; see also [[humangate-review-is-not-real-escalation]] and [[drain-is-a-resident-daemon]].
- **`test` is the only required check.** `cla` and `Workers Builds: web-everything` are non-blocking (fail freely). Everything waits on `test` — but since #2290 **`pr-land` no longer merges at all**: it labels `ready-to-merge` on green and the drain, the sole writer to `main`, lands it. The `gh pr merge`-it-yourself steps below are the pre-#2290 shape and are retired; never merge your own PR.
- **Concurrent lands cause "BEHIND main / strict up-to-date" races.** Branch protection requires up-to-date, and other sessions land PRs continuously, so a lane ref goes stale mid-flight. Since #2284 the producer no longer aborts on it — `pr-land` labels a BEHIND-but-green PR and hands it to the drain, which rebases before merging, so `reason:"behind"` is not reachable from `/pr` (a behind-and-not-yet-green PR ends in `check-timeout` instead). When you *do* need to re-parent by hand (a real `conflict`, or a stuck ref): **re-parent the changeset onto the latest `origin/main` and merge fast** (`git rebase` is blocked by the routinely-dirty tree, so use plumbing). Two plumbing forms:
  - **Preferred — temp-index (build exactly origin/main + only your files):** `export GIT_INDEX_FILE=$(mktemp -u); git read-tree origin/main; for f in <your files>; do B=$(git hash-object -w "$f"); git update-index --add --cacheinfo 100644,"$B","$f"; done; TREE=$(git write-tree); C=$(git commit-tree $TREE -p origin/main -m "$MSG"); unset GIT_INDEX_FILE; git push --force origin "$C:refs/heads/lane/<slug>"`. Clean and contamination-proof.
  - **Avoid `git merge-tree --write-tree origin/main HEAD` for a *focused* PR** — it merges ALL of your diverged local `HEAD`, so if local main carries superseded/stale commits it sweeps their diffs (e.g. a stale `backlog/NNN.md`) into the PR. It bit me: a skill PR silently reverted a concurrent `backlog/2162` edit. Only safe when local `HEAD` is exactly origin/main + your one change.
  - Then hand it back to the drain (re-run `pr-land` on the same `--ref`; **never** `gh pr merge` yourself, #2290). **Don't re-push after the last rebase** — a force-push restarts CI (~2.5min) and you fall behind again; if only the check is pending (state BLOCKED, not BEHIND), just wait for `test`.
- **`gh pr merge --admin` is denied** by the auto-mode classifier (bypasses review on your own PR). Don't reach for it — win the up-to-date race instead.
- **Local `main` ends up diverged** (your pre-rebase commit is superseded by the merged one) while the tree stays dirty with others' work. `git reset --hard` is (correctly) blocked — it'd discard others' uncommitted baseline. Leave local main as-is; the work is on origin. See [[shared-index-commit-race]].
- **`gh pr create` can 401 on GraphQL while everything else works** (2026-07-02, landing #2181). `gh pr create` is a GraphQL *mutation* and intermittently returns `HTTP 401 Requires authentication` even though `gh api user` (REST), `gh api graphql {viewer}` (GraphQL read), and `gh pr merge` (GraphQL mutation) all succeed with the same keyring token (`repo` scope, `push:true`). Not an env-token override. **Workaround: create the PR via REST** — `gh api -X POST repos/<o>/<r>/pulls -f title=… -f head=lane/<slug> -f base=main -f body=…` — then re-run pr-land: it finds the now-open PR (`gh pr list --head`, REST) and skips straight to wait→label→handoff. pr-land itself has no REST-create fallback yet (only `--fallback-git`, which bypasses the CI gate); the REST-create-then-rerun is the clean path.
- **pr-land now self-heals new-item id collisions (#2181, 2026-07-02).** After a clean merge it runs `scripts/backlog-renumber-collisions.mjs` (NO `--base-ref`) on post-merge main; a duplicate NNN → the just-merged (newest) file yields to next-free, gated + committed + pushed (never force). So a manual/`/pr`/`/drain` land no longer needs a hand-renumber like PR #12 did. `--no-heal` opts out. A heal problem is surfaced but never fails the land. Was workflow-only before (the #2071 batch integrator).
