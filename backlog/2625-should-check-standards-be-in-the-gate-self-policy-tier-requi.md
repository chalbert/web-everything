# Should check-standards be in the gate-self / policy tier (require review:human)?

Editing the repo-health gate [we:scripts/check-standards.mjs](../scripts/check-standards.mjs) (and its rule pack [we:scripts/check-standards-rules.mjs](../scripts/check-standards-rules.mjs)) today scores only **blast-radius** → `review:pending`: it escalates and runs an elevated-care panel, but a converged **agent** may clear it — no human needed. So an agent can soften the gate that defines "green" and self-clear. Should the gate join the **policy tier**, forcing `review:human`? Grounded in the real trust-chain machinery, prep finds the title bundles **two** questions — one already settled (a red gate already hard-blocks merge), one a genuine four-option placement fork whose best answer is a **contract-split**, not a blunt tier flip.

## Decision (2026-07-28) — RATIFIED: (d) contract-split

Operator ruled **fork (d) — contract-split** (the option the raw a/b fork missed and prep surfaced). **Keep BOTH `check-standards` `.mjs` files** (the impl `we:scripts/check-standards.mjs` + the rule pack `we:scripts/check-standards-rules.mjs`) in the **ENGINE tier** — agent-clearable, so the repo's two most-churned files (79 + 57 commits/yr) are not stranded behind a human. **Move the *definition of green*** into a **POLICY-tier `we:scripts/check-standards.contract.json`**, mirroring the ratified `we:scripts/lib/review-policy.contract.json` / loader split. A conformance suite pins impl↔contract, so a behaviour-preserving impl refactor stays agent-clearable while a genuine weakening of the definition trips the policy path → `review:human`. This closes the "an agent weakens the gate then self-clears" ([#809](/backlog/809-)-class self-approval) hole **without** over-gating the hot impl files.

**Codified as a REUSABLE precedent** (the operator's key point — "exactly the path to take in similar decisions"): for *any* "which trust tier owns X" decision where X is a gate/validator/definition an agent could weaken then self-clear, the **default path is contract-split** — engine-tier the impl code, policy-tier a `we:*.contract.json` for the definition. Statute: [we:docs/agent/platform-decisions.md#contract-split-for-tier-ownership](../docs/agent/platform-decisions.md#contract-split-for-tier-ownership). These are small, patterned micro-decisions well suited to on-card surfacing in the future decision UI ([#2577](/backlog/2577-)) rather than a full prepare/preview cycle.

**Graduation (follow-on impl):** the actual extraction — mint `we:scripts/check-standards.contract.json`, register it `tier: 'policy'` + both `.mjs` files `tier: 'engine'` in `we:scripts/lib/gate-config.mjs`, and add the conformance suite — is impl work tracked as its own child item [#2769](/backlog/2769-) (`graduatedTo`); this decision ratifies the *approach*, not the code.

## Grounding — the real machinery (concrete refs)

The auto-review trust chain is explicit versioned config in [we:scripts/lib/gate-config.mjs](../scripts/lib/gate-config.mjs), with **two tiers** (`TRUST_CHAIN`, lines 66–171):

- **policy tier** (`tier: 'policy'` → `isPolicyCorePath`, re-exported as `isGateSelfPath` in [we:scripts/lib/review-escalation.mjs](../scripts/lib/review-escalation.mjs):151) — the code that **decides whether the review gate fires and what clears it**: the rubric (`we:review-escalation.mjs`), the disposition router (`we:review-core.mjs`), the policy contract, the roster itself. An edit here forces `review:human` (`scoreEscalation` sets `humanRequired`, lines 270–275; `decideReviewGate` parks `review:human`, lines 537–539). The file header is emphatic: *"Keep the POLICY tier MINIMAL: `review:human` = 'human judgment essential', not merely 'important' — a wider policy net just re-strands the queue on humans. Only code that decides whether the gate fires and what clears it is `policy`."*
- **engine tier** (`tier: 'engine'`) — the **lander** (`we:merge-ai-prs.mjs`) and the resident drain daemon. It **obeys** the gate rather than defining it, so it always escalates + runs the full adversarial panel, but a converged agent verdict may clear it.

The gate script [we:scripts/check-standards.mjs](../scripts/check-standards.mjs) is registered in **neither** tier. It matches only the generic `^scripts\/` blast-radius pattern ([we:scripts/lib/review-escalation.mjs](../scripts/lib/review-escalation.mjs):79), so `isBlastRadiusPath` is true → `scoreEscalation` returns `escalate: true, humanRequired: false` → the producer stamps `review:pending` ([we:scripts/pr-land.mjs](../scripts/pr-land.mjs):700, via `producerReviewLabel`). Care-level lands at **elevated** (blast-radius weight 3, `CARE_BANDS.elevated = 3`), so the panel already looks harder — but stays agent-clearable.

## Settled by existing machinery — a red gate already hard-blocks merge (NOT a fork)

The title's "should a red `check:standards` be a **hard merge gate**" half is **already yes by construction**, so it is not a live fork. The required aggregating CI check **`test`** runs `npm run check:standards` as its *"Repo health gate"* step ([we:.github/workflows/ci.yml](../.github/workflows/ci.yml), job `test`). A red gate ⇒ red `test` check ⇒ (i) branch protection blocks the merge, and (ii) the lander refuses it (`isRequiredCheckGreen(pr, 'test')` is false, [we:scripts/merge-ai-prs.mjs](../scripts/merge-ai-prs.mjs):323). You therefore **cannot** silently ship a non-conformant tree: to land, the gate must be *green*, which means a weakening PR must actually **edit the gate script** (and delete any rule's guarding test) — bringing it onto the escalation path above. The only open question is what tier that edit path is.

## Fork 1 — which trust tier does the gate script belong to?

*Fork-existence:* the gate's edit path resolves to exactly one clearance regime and they cannot coexist — human-only (a), rostered-agent-panel (b), incidental-agent-panel (c), or a split that human-gates only the definition-of-green while leaving the impl agent-clearable (d). Each carries a different `who-may-clear` rule, so this is a real either/or, not a support-both.

- **(a) policy tier — `review:human` on every gate edit.** Register the gate script + its rule pack as `tier: 'policy'`. A human must approve any change to the gate. Closes the residual hole by construction — an agent can never weaken *and* self-clear the definition of green. This is the item's original lean. (Note the parent-precedent cuts the *other* way once ground: #2448's two-tier flip made the lander/transport **engine-tier — agent-clearable** — and reserved `review:human` for the review-*decision* machinery alone; so "by analogy to #2448" actually argues for engine, not policy. The honest case for (a) is not precedent but the self-referential worry in the Skeptic note below.)
- **(b) engine tier — rostered, always-escalates, agent-clearable.** *(the floor — subsumed by (d))* Register both files in `TRUST_CHAIN` as `tier: 'engine'`, exactly like the lander. The gate script then **always** escalates and runs the **full adversarial panel** by intentional roster entry (not incidentally via a `^scripts\/` regex), and the guarantee **travels by basename** if the file ever relocates — but a converged agent verdict still clears it, so routine gate work (new lints, rule tweaks) is not stranded on a human.
- **(c) status quo — unrostered blast-radius.** Leave both files matched only by `^scripts\/`. Already escalates + runs an elevated-care panel + agent-clearable; the write-time `PreToolUse` hooks and the gate's own tests are the other guards. No roster entry, no human teeth, protection stays incidental to the regex.
- **(d) contract-split — human-gate the *definition of green*, keep the impl agent-clearable.** *(recommended default)* Mirror the pattern already in the roster (`we:review-policy.contract.json` is `policy`/human-gated while its bulky loader `we:review-policy.mjs` stays agent-clearable behind a conformance suite, [we:scripts/lib/gate-config.mjs](../scripts/lib/gate-config.mjs):82–94). Extract the *semantic* thresholds/rule-set that define "green" out of the 258 KB of impl into a small `we:check-standards.contract.json`, register **that** as `tier: 'policy'` (a real weakening of green now forces `review:human` — and the contract is rarely edited, so no queue-stranding), and register the two `.mjs` files (impl + rule pack) as `tier: 'engine'` (the (b) floor — always escalates, agent-clearable, so routine lint/rule churn is not stranded). A conformance suite proves the impl realizes the contract, so an impl refactor stays green/agent-clearable while a definition change is red → forces a contract edit → human.

**Tradeoff.** Defense-in-depth vs review friction vs classification fidelity — and (d) is the split that stops forcing a choice between them. (a) has real teeth but **mis-fits the policy tier's own definition**: the policy tier exists for the *review-clearance* conflict-of-interest ("an agent policing its own leash"), and the gate script does **not** decide whether the review gate fires or what clears it — it defines *conformance*, a different leash. And the rule pack [we:scripts/check-standards-rules.mjs](../scripts/check-standards-rules.mjs) (145 KB) + [we:scripts/check-standards.mjs](../scripts/check-standards.mjs) (113 KB) are the repo's **most-churned files by a wide margin** (79 + 57 commits/yr — ~2× the busiest existing policy-tier file, `we:review-core.mjs` at 33/yr; every new lint touches them), so (a) would strand a large share of ordinary backlog work on a human — precisely the *"re-strand the queue on humans"* cost the tier's own header warns against. (c) is nearly free but leaves the gate's protection *incidental* to a regex a future refactor could narrow (silently dropping escalation with no failing test — the exact un-anchoring failure #2448 was built to kill), and un-audited. (b) fixes that anchoring — a gate-critical piece the agent **obeys/produces** but does not use to police its own review-leash → engine tier, panel-clearable, explicitly rostered — but on its own it **does not close the item's stated hole**: an agent can still weaken green and self-clear via a converged panel. (d) closes that hole *and* dodges (a)'s friction by splitting the file: only the small, rarely-edited **definition of green** is human-gated; the churny impl stays agent-clearable behind a conformance suite.

**Default: (d) contract-split, with (b) as the floor.** Register both `.mjs` files as `engine` (the anchoring + always-escalate win of (b)), and extract the definition-of-green into a `policy`-tier `we:check-standards.contract.json` so a genuine weakening of the gate forces `review:human` while routine impl/lint churn does not. This is the only option that answers the item's actual worry ("agent weakens the definition of green and self-clears") **without** the over-reach of (a): it puts the human exactly where the irreducible judgment is (what counts as green) and nowhere else. It reuses a pattern already ratified in the roster (the `we:review-policy.contract.json` / loader split, [we:scripts/lib/gate-config.mjs](../scripts/lib/gate-config.mjs):82–94), so it is precedented, not novel. Left **OPEN** for the human — the crux is whether the residual "agent weakens green + self-clears" hole is worth the one-time cost of extracting a `we:check-standards.contract.json` + its conformance suite (→ (d)), or whether the existing hard-red-gate + adversarial-panel + write-time-hooks + gate-tests stack already makes the hole acceptable and only the cheap anchoring of (b) is warranted.

*Skeptic (four-axis attack, run in prep):* **(b)-as-drawn SURVIVES-WITH-AMENDMENT → the amendment IS option (d).** Axis-0 (classification): partly lands — calling the gate "engine, parity with the lander" is a *loose* analogy (the tiers are defined around the *review* gate; check-standards is an orthogonal CI gate the review machinery never references), and for this WE-permanent file the "travels" benefit is moot, so (b)'s delta over (c) is near-zero — but not literally zero (it pins escalation against a regex narrowing, a real durability win). Axis-1 (merit): **lands** — (b) leaves the file agent-clearable, so it does *not* close the item's hole; that is what forces the amendment to (d). Axis-2 (precedent): does **not** land, it boomerangs — #2448 put the lander in `engine` (agent-clearable), so the real precedent argues engine/contract-split, not (a). Axis-3 (friction): does **not** land — the 79 + 57 commits/yr churn is real, so (a)'s human-on-every-edit cost is the header's explicit anti-goal, not overstated. Net: (a) is refuted (no COI + strands the two hottest files); (c) is nearly-right but leaves escalation incidental; **(d) is the answer the raw fork missed** — it is exactly the roster's existing contract/loader split applied to the gate. Statute-overlap check: the tier definitions live in [we:scripts/lib/gate-config.mjs](../scripts/lib/gate-config.mjs) (config, not [we:docs/agent/platform-decisions.md](../docs/agent/platform-decisions.md)); no `codifiedIn` collision — a resolution would cite `#deterministic-core-thin-judgment` and #2448/#2445 as lineage, not author a competing statute anchor.

*Screen: clear.* (1) Impl-detail across a boundary? No — trust-tier placement (and the contract/impl split) is a governance/policy call, not a WE↔FUI implementation detail. (2) Merit vs prioritization with both branches free-to-build? A genuine merit difference remains: (a)/(d) vs (b)/(c) is *whether a human must clear a weakening of the definition of green* — a standing safety-vs-friction merit call, not "build it later." (Fresh-context screen noted a faint self-referential angle — the review panel's own clearance authority rests on a green gate — which is a real, if weaker, echo of the policy-tier COI; (d) neutralizes it precisely by human-gating only the definition, not the impl.)
