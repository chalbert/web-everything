# Conveyor-only dispatch-origin attribution, so velocity/throughput can be measured for the mechanical engine alone (and a queue-runway forecast on top)

Grounded 2026-09-07: we:scripts/readiness/velocity-metrics.mjs (#2686) already computes real throughput (points/wk, items/wk over a trailing window) plus cycle-time and WIP-split, purely from backlog dateOpened/dateStarted/dateResolved/size -- but it has NO notion of dispatch origin at all: every resolved item counts toward throughput regardless of whether its build was launched by the conveyor's own mechanical tick (the conveyor's own bridge and spawn scripts -- see the CORRECTION paragraph below: there is NO single conveyor dispatch surface today) or hand-dispatched by an interactive session's own Agent-tool/claude-bg call (which leaves no repo-side record at all). So today's throughput number conflates the two, and a session-driven burst (like the one that filed this very card) inflates it in a way that says nothing about steady-state mechanical capacity -- the thing the operator actually wants to track toward the long-term goal of the interactive session disappearing entirely. Separately, we:scripts/readiness/conveyor-instrument.mjs (#2680) already has a mark-dispatch/mark-setup CLI writing a we:.conveyor/dispatch-log.json sidecar keyed by item num -- built for a DIFFERENT purpose (decomposing per-item wall-clock latency into authoring/setup/firstCi/land phases for a throughput-lever go/no-go) but CONFIRMED DEAD: no caller anywhere invokes mark-dispatch or mark-setup, and no we:.conveyor/dispatch-log.json exists on disk. Wiring the dispatch-lane operation's effect-apply step (we:scripts/operations/dispatch-lane-io.mjs) to stamp a per-item dispatch-origin marker would reuse the dead primitive's mechanism rather than invent a third one -- BUT that stamp site only covers dispatches that pass through the operation, and (see CORRECTION) that is not yet the live path, so "unstamped = session-driven by elimination" is NOT valid today. CORRECTION (2026-09-19, PR #2027 review round 1; the original grounding called we:scripts/operations/dispatch-lane.mjs "the SOLE conveyor dispatch surface" -- that is false against current code and docs): (1) The conveyor's live BUILD dispatch is still the main-session bridge, not the dispatch-lane operation: we:skills-src/conveyor/SKILL.md step 3 has the bridge spawn one background delivery agent per surfaced decisions.spawnBuilds entry with the harness Agent tool, and the card that reroutes it, we:backlog/3096 (route the conveyor's build dispatch through the declared dispatch-lane operation), is status open and blocked by we:backlog/3353 (harden the liveness readings, then make the first live dispatch), also open -- so the dispatch-lane operation (registered in we:scripts/operations/run.mjs) has made no live conveyor dispatch yet. (2) The four files this card originally named as its callers do not call the operation: we:scripts/conveyor/tick-core.mjs only plans (it emits decisions.spawnBuilds; it names we:scripts/operations/dispatch-lane.mjs in comments and mirrors its session-slug grammar but does not import it); we:scripts/conveyor/reconcile-pass.mjs and we:scripts/conveyor/session-reaper.mjs import only helpers such as defaultListAgents from we:scripts/operations/dispatch-lane-io.mjs; we:scripts/conveyor/lease-reaper.mjs imports only a grace-period constant from we:scripts/operations/dispatch-lane.mjs. (3) A second conveyor spawn path exists outside the operation: we:scripts/conveyor/reconcile-fix-dispatch.mjs spawns fix agents itself (its own spawnAgent call), reusing we:scripts/operations/dispatch-lane.mjs's fillBrief/sessionSlugFor and we:scripts/operations/dispatch-lane-io.mjs's argv and spawn helpers. (4) Consequence for this decision: there is no single conveyor dispatch chokepoint today, so a stamp placed only at we:scripts/operations/dispatch-lane-io.mjs's effect-apply step would mark only dispatches that go through the operation (currently none) and would leave the bulk of real conveyor builds unstamped, wrongly reading as session-driven under "unstamped = session-driven by elimination". The mechanism (a durable per-item stamp) is unchanged; the stamp SITE and the sequencing are now part of the decision -- see the sub-question added to FORK 1. FORK 1 (the real design fork): HOW is the stamp made durable enough for multi-week velocity trend analysis, not just #2680's original fine-grained recent-window latency use? (a) resurrect the we:.conveyor/dispatch-log.json sidecar as-is and have we:scripts/readiness/velocity-metrics.mjs join on it -- fastest, reuses dead code verbatim, but the sidecar is explicitly documented as gitignored/ephemeral ('a small signal, not a durable store'), so a lane-pool litter reap (we:backlog/3568) or a fresh clone could silently lose dispatch history a velocity trend depends on; (b) stamp a lightweight field directly onto the backlog item's own committed frontmatter at dispatch time (e.g. dispatchOrigin: conveyor, mirroring how dateStarted is already stamped) -- durable by construction (committed data, the same single-source-of-truth convention we:scripts/readiness/velocity-metrics.mjs already reads), costs one new optional field, absent-safe for every item filed before this lands; (c) infer origin post-hoc from session-slug or PR-metadata heuristics -- rejected outright, it fights the same no-fabricated-precision principle both #2686 and #2680 already establish in their own file headers. SUB-QUESTION (added by the correction): WHERE is the stamp written? (i) At the dispatch-lane operation's effect-apply step -- correct only once we:backlog/3096 and we:backlog/3353 land so every conveyor build passes through the operation, so the follow-on must be sequenced behind them. (ii) At every spawn site that exists today (the SKILL bridge's Agent-tool spawn, we:scripts/conveyor/reconcile-fix-dispatch.mjs's spawn, and the operation) -- correct now, but three write sites that can drift apart. (iii) At the tick's plan step (we:scripts/conveyor/tick-core.mjs records nextState.buildGuards for every surfaced spawnBuild, so it sees every planned conveyor build regardless of who spawns it) -- but it records a PLANNED spawn, not a confirmed one, so it would need the planned-vs-confirmed reconciliation tick-core already does for its own guards. RECOMMENDED STAMP SITE: (i), with the follow-on blocked on #3096/#3353, because it makes "unstamped = session-driven" actually true and keeps one write site; until those land, do NOT read the absence of a stamp as evidence of session-driven work. RECOMMENDED DEFAULT: (b), the durable frontmatter stamp -- velocity is inherently a historical-trend metric, and the repo's own state-lives-where-its-nature-dictates convention (we:docs/agent/platform-decisions.md#state-lives-where-its-nature-dictates) says durable per-item facts belong in the committed item, not a gitignored sidecar. Once ratified, the mechanical follow-on (build-ready, no further fork) is: (1) we:scripts/operations/dispatch-lane-io.mjs stamps the marker at effect-apply, (2) we:scripts/readiness/velocity-metrics.mjs's gatherItems/rollUp gains an origin filter so --origin=conveyor reports throughput for JUST mechanically-dispatched work. FORK 2 (a further follow-on slice, noted per the operator's own mid-session extension, NOT built now): once real conveyor-only throughput exists, forecast a queue-runway (ready-and-dispatchable queue depth divided by the measured conveyor-only dispatch rate = time until the queue runs dry) -- directly motivated by tonight's real incident, where the queue looked thin and needed manual investigation to find it was mostly stale already-done noise, not real scarcity. A naive raw-queue-length numerator would reproduce that exact confusion. we:scripts/readiness/dispatch-plan.mjs already computes the fix: its held-reason vocabulary (HELD_REASONS) already separates real capacity-bound holds (no free lane, overlaps lane-N) from non-work noise (already-done -- #3457/#3460's own age-gated ground-truth fix for exactly this incident class, blocked, needs-slice, needs-decision, unshaped-no-scope, branch-drift-blocked). RECOMMENDED DEFAULT for the runway depth definition: genuinely-dispatchable depth = launch.length + count of items held ONLY for no-free-lane/overlaps-lane-N reasons (real work blocked purely by capacity, not by noise) -- reusing we:scripts/readiness/dispatch-plan.mjs's existing classification rather than a new one. This makes Fork 2's depth question NOT a real open fork (we:dispatch-plan.mjs already draws the exact line tonight's incident needed) -- so once Fork 1 is ratified and the conveyor-only throughput denominator exists, the runway estimate (depth-count / conveyor-only items-per-day) is a small build-ready story, not a second decision. Distinct from we:backlog/3569 (the rolling-24h capacity monitor: lane utilization / queue depth / dispatch rate / heavy-admission concurrency) -- #3569 is explicitly current-state capacity, never throughput/velocity, and its own text does not claim this ground; this item is a sibling that should cross-reference #3569 (both may eventually read the same underlying dispatch-log/frontmatter signal) rather than be folded into it, since #3569's done-when is capacity-shaped and forcing velocity/runway into it would blur that.
