## Decided design
Everything below is either already ratified (cited, not re-opened) or a small implementation default named here per the "never bury a fork" rule — none of it requires unbuilt code to settle.

1. **Interaction frame: MASTER-DETAIL.** Ratified at the epic (#2705) — not reopened here.
2. **Keyboard model: `aria-activedescendant`, per DEC #2719 (ruled 2026-07-27, a `plateau-app:read-model.ts` constant).** This is the one place a naive builder is most likely to go wrong, because **the only rendered reference for this screen (the epic's "Live integrated page" artifact) implements the OLD, superseded default (roving `tabindex`)** — each row gets `tabindex="0"/"-1"` and receives real DOM focus via `.focus()`. The DEC ruling explicitly changed this default *because* of virtualization (S10/#2724): focus must stay on the listbox container so a row leaving/entering the render window never strands it. Concretely, S1b must build:
   - the scan listbox container (`role="listbox"`) itself carries `tabindex="0"` and `aria-activedescendant` pointing at the active row's element id.
   - Each row needs a real, stable `id` attribute (not just the mock's `data-id`) — `aria-activedescendant` targets an element id.
   - Rows carry **no** `tabindex` of their own; arrow/Home/End/Enter keydown handling lives on the **listbox container**, not per-row.
   - The DOM otherwise reuses the mock's structure/CSS classes (list/row/option roles, the where-the-time-goes bar, kind glyph, forecast chip) as a grounded starting point — only the focus/keyboard mechanics change, not the visual layout.
3. **Honest-forecast: the three-branch rule**, already frozen as data in the landed `plateau-app:src/feature-tracker/feature-tracking.webcases.ts:138` (the `FT_FORECAST_RULE` export) by #2716/S0r: PROJECTION (window, never a date) / DELIVERED (real past date only) / ABSENCE (no date — blocked/gated/stalled/below-sample-floor). The Drain Daemon fix below is this rule's concrete acceptance case.
4. **The Drain Daemon honesty bug — a real, verified defect in the reference artifact, not a hypothetical.** The "Live integrated page" mock's own fixture is dishonest on exactly the invariant this slice must enforce: its Drain Daemon entry is flagged blocked (upstream = conveyor) **and** carries a typed future landing date. `plateau-app:data.ts`'s mock fleet fixture must NOT reproduce this: the Drain Daemon row (and every blocked row) must carry a `'gated'` landing state with no date. This is a concrete, testable regression case for `plateau-app:data.test.ts`.
5. **`plateau-app:data.ts` / S1a's `plateau-app:read-model.ts` boundary — don't copy the mock's mutation pattern.** The reference mock derives its blocked/blocking edges by mutating the raw feature objects in place at load time — this is literally "the v3 render-order global bug" #2718/S1a is chartered to kill (a bottleneck-id global as a side-effect of render order). `plateau-app:data.ts` owns only the RAW fixtures — a features array (no pre-computed blocked/blocking edge fields) and an edges list (upstream→downstream pairs) — and must not compute or mutate derived edges itself; that derivation is S1a's pure read-model functions, taking the raw data as input.
6. **Header banner slot (S8) — S1b owns the container, S8 owns the content.** S1b renders an empty, hidden placeholder inside the fleet header with a stable id (structure lifted from the reference mock's bottleneck-banner element). S8 (`plateau-app:src/feature-tracker/banner.ts`, #2723) looks it up by that id and fills/unhides it — the same plain-DOM-id handoff every other mount in this app uses (no bespoke registration API to invent; e.g. `plateau-app:src/main.ts:696` looks up the Backlog view's mount point by id).
7. **Theme toggle — reuse the existing app-wide mechanism, don't invent a screen-local one.** `plateau-app:src/backlog-view/lane-board.ts:60-91` already implements a theme toggle under a shared storage key, explicitly commented **"not a board-scoped name, so a future sibling console screen can read the SAME choice instead of inventing its own key."** An `effectiveTheme()` reader is exported from that module; the small persist/apply helpers are not. **Default (small, low-stakes call, named not buried):** the new mount module imports the exported theme reader and locally re-implements the ~3-line "persist to storage + stamp the theme attribute on the document root" toggle logic against the same literal storage key, rather than exporting the apply-helper + key constant out of `plateau-app:src/backlog-view/lane-board.ts` into a shared module. Reasoning: the duplication is tiny (one string constant + one setter), and extracting a shared theme module would pull `plateau-app:src/backlog-view/lane-board.ts` into this slice's scope for a cosmetic refactor unrelated to its own acceptance. If a **third** screen needs the same toggle, that's the trigger to extract it for real — noting it here so it isn't silently lost.
8. **Route + nav placement:** a new top-level route, nav label "Feature Tracking", inside the existing "Plateau Loop" nav section — see Scope above.
