# dispatched review/fix sessions get the App token via a per-call-refreshing `gh` shim, not inherited env

Live-caught 2026-09-23 investigating plateau-app PR #181's review session failure (`GraphQL: API rate limit already exceeded for user ID 760299` — the operator's own personal GitHub account, not the App).

**CORRECTED ROOT CAUSE (this item's own first cut, below, was wrong — kept for the record).** The first pass here concluded the GitHub App installation (App id 5037855, installation id 163880042) had never been granted the permissions/repos `we:scripts/lib/github-app-auth-env.mjs#REQUIRED_APP_PERMISSIONS`/`REQUIRED_APP_REPOS` require, so `ensureFreshGithubAppEnv` never applied a token at all. That was true for the specific window of log lines read at the time, but it was NOT the standing defect: the operator has since granted the installation's permissions and repo access, `ensureFreshGithubAppEnv` now genuinely mints and applies (`{"applied":true,"reason":"ok"}`, confirmed live), and PR #181's review session STILL would have failed the same way, because of a second, independent gap the first pass never reached: **`claude --bg` does not inherit the spawning process's ambient `process.env`.** Live-confirmed by direct process inspection (`ps eww` on the review daemon (pid 88701), the fix-dispatch daemon (pid 8004) and the drain (pid 43551) — all three carry `WE_GITHUB_APP_*`/`GH_TOKEN` — versus two live dispatched review sessions (pids 72738, 81880), which carried NEITHER) and reproduced here with a throwaway probe session: an env var set on the spawning shell never reaches a `--bg` session's own Bash-tool subprocess environment. `we:scripts/operations/review-dispatch.mjs`/`we:scripts/conveyor/reconcile-fix-dispatch.mjs`'s own wiring, and `we:scripts/operations/dispatch-lane-io.mjs#defaultSpawnAgent`'s plain env inheritance, were both already correct for THIS process's own `gh` calls — the daemon's own ticks. What was missing was ANY mechanism at all for a dispatched session's OWN `gh` calls, since those run in a session `claude --bg` starts that is not a simple child of the daemon process.

**WHAT ACTUALLY REACHES A `--bg` SESSION, confirmed live by direct experiment**: `claude --bg --settings '{"env":{...}}'` — an explicit CLI argument, not inherited env — sets exactly those vars in the started session's own Bash-tool subprocess environment, including a `PATH` override (proven by shadowing `gh` with a fake executable and observing the fake respond from inside a real dispatched session).

**WHY A PATH-SHADOWING `gh` SHIM, NOT A ONE-TIME `GH_TOKEN` VALUE BAKED INTO `--settings`.** An installation token lives ~1h; a dispatched review/fix session can genuinely outlive that. A `we:scripts/lib/gh-app-shim.mjs`-generated wrapper shadows `gh` on `PATH` and reads the shared, continuously-refreshed token cache (`we:scripts/lib/github-app-auth-env.mjs`'s own cache file) FRESH on every `gh` invocation — never a stale spawn-time snapshot, and never the private key itself (only the already-minted, short-lived cached token). Wired once, at the shared sink (`we:scripts/operations/dispatch-lane-io.mjs#buildAgentArgv`'s new `settingsEnv` param, resolved by `we:scripts/operations/dispatch-lane-io.mjs#resolveGhShimSettingsEnv`), so both `we:scripts/operations/review-dispatch.mjs` (via `createDispatchSinks`) and `we:scripts/conveyor/reconcile-fix-dispatch.mjs#dispatchFix`'s own fresh-dispatch call site get it — but NEVER on `we:scripts/conveyor/reconcile-fix-dispatch.mjs#tryResumeFix`'s `--resume` branch, which must stay a bare `--bg --resume <id>` (any other flag makes the CLI fork a copy instead of resuming, per that function's own docblock) and does not need it anyway: a resumed session is the SAME still-running process its original fresh dispatch already gave the PATH override to, and the shim re-reads the cache fresh on every call regardless of session age.

**OPT-IN, SAME GATE AS #3866.** `we:scripts/lib/gh-app-shim.mjs#buildGhShimSettingsEnv` returns `null` — no fs write, no `--settings` — unless the CALLING process itself has `WE_GITHUB_APP_*` configured, reusing `resolveGithubAppEnvConfig` rather than a second opt-in check. A host that has not configured App auth (every CI run, every developer shell) gets a dispatch byte-identical to before this file existed.

**A SECOND LIVE-CAUGHT BUG WHILE BUILDING THIS FIX, FIXED IN THE SAME PR**: this item's own FIRST version of the status-recording fix (`we:scripts/lib/github-app-auth-env.mjs#ensureFreshGithubAppEnv`) wrote to the real, shared token-cache status file on every call by default — and this suite's own pre-existing tests, none of which had any reason to know status recording exists, silently exercised that real default and stomped the real daemon's own `applied:true`/`insufficient-access` with a misleading `not-configured` on every local test run. Fixed two ways: (1) `not-configured` is now never recorded at all (it describes the caller, not the fleet's installation — a reader with no file at all already gets its own honest, distinct message); (2) every pre-existing test that reaches a reason that IS recorded now injects an explicit no-op `writeStatus`, so no test in this repo touches the real home directory for this. See that file's own `record` docblock and this suite's own header comment for the full account — including why an attempted `vi.mock('node:os', ...)` fix was tried and discarded (this suite's `environment: 'happy-dom'` resolved the SUT's own `homedir()` import through a different path than the test file's, so the mock silently never reached it).
