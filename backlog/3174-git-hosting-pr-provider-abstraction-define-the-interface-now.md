# Git hosting/PR provider abstraction — define the interface now, defer multi-provider live testing

Motivated by tonight's (2026-08-17) repeated GitHub GraphQL outages stalling PR creation/labeling/merging across the whole operations-engine delivery loop -- git push itself never failed (SSH, unaffected), but we:scripts/pr-land.mjs, we:scripts/merge-ai-prs.mjs, we:scripts/review-set-label.mjs, and the review-label state machine (review:pending/accepted/changes, ready-to-merge, ci:failed) are all written directly against the gh CLI / GitHub REST+GraphQL, with no seam between operations-engine logic and the concrete provider. This falls under #2626's already-ratified vendor-abstraction hard-requirement (any vendor-specific integration needs an abstraction), applied to git hosting specifically, and mirrors the same files-as-code-today/pluggable-service-later shape already discussed for the backlog store. Operator-scoped this in discussion (2026-08-17): the abstraction LAYER (a provider interface -- createPR/setLabel/listChecks/merge/etc -- with GitHub as the sole live binding) is a near-term, tractable step; a SECOND live provider actually configured and tested end-to-end is explicitly NOT in scope here -- that needs real accounts on other providers and is a separate, heavier decision. Important distinction to keep visible through prepare/ratify: defining the interface alone does not buy outage resilience (tonight's stalls would recur identically with only GitHub wired even after this item lands) -- the payoff of THIS item is portability/testability, not failover; failover is a distinct future item once/if a second provider is actually stood up. Needs prepare before ratification per #39 -- open questions to resolve in prep: how much of the review-label state machine generalizes cleanly across providers (GitLab has labels too; a raw email/ticket-based host would not), where the seam should live relative to we:scripts/operations/ (a new provider-facing adapter alongside the existing CLI/HTTP calling-axis adapters (MCP is discussed as a possible future third but has no adapter built and no grep hits in we:scripts/operations/ today), or a lower-level module every operations script imports), and whether this is worth doing now versus after some of #3029's still-open surface lands -- 18 of its 37 children are open as of this filing (including #3033's own ratify slice), not just one; #3036's HTTP adapter is the one specifically resolved earlier today, 2026-08-17.

## Done when

1. **Prepared** — a prep pass (per we:docs/agent/backlog-workflow.md's prepare step) lays out the fork concretely: where the provider seam lives relative to we:scripts/operations/ (a new adapter alongside the existing CLI/HTTP calling-axis adapters -- MCP is discussed as a possible future third but has no adapter built today -- vs. a lower-level module every operations script imports), which operations-engine call sites (we:scripts/pr-land.mjs, we:scripts/merge-ai-prs.mjs, we:scripts/review-set-label.mjs, we:scripts/conveyor/infra-blocked.mjs, and any others found by a full grep for `gh ` invocations) the interface must cover, and an honest assessment of how much of the review-label state machine (review:pending/accepted/changes, ready-to-merge, ci:failed) generalizes across a non-GitHub provider versus is GitHub-specific.
2. **Ratified** — the operator records a ruling (per #39, never ratified unprepared) on whether/when to build the interface now versus sequence it after some of #3029's still-open surface lands (18 of 37 children open, including #3033's ratify slice), given the overlapping surface.
3. If ratified to proceed: the interface exists with GitHub as its sole live binding, every call site named in criterion 1 routes through it (no direct `gh`/GitHub-REST call remains in operations-engine scripts), and existing tests for those scripts pass unmodified in behavior (this is a refactor of the seam, not a behavior change — no second provider is stood up or tested as part of this item).
