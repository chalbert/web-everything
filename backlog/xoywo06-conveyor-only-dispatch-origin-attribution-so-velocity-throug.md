# Conveyor-only dispatch-origin attribution, so velocity/throughput can be measured for the mechanical engine alone (and a queue-runway forecast on top)

Grounded 2026-09-07: we:scripts/readiness/velocity-metrics.mjs (#2686) already computes real throughput (points/wk, items/wk over a trailing window) plus cycle-time and WIP-split, purely from backlog dateOpened/dateStarted/dateResolved/size -- but it has NO notion of dispatch origin at all: every resolved item counts toward throughput regardless of whether its build was launched by the conveyor's own mechanical tick or hand-dispatched by an interactive session's own Agent-tool/claude-bg call -- and today NEITHER of those writes any repo-side record, because at the dispatch surface they are the SAME mechanism. (An earlier draft of this card, and the commit message that filed it, claimed we:scripts/operations/dispatch-lane.mjs is the SOLE conveyor dispatch surface, "invoked ONLY by" we:scripts/conveyor/tick-core.mjs / we:scripts/conveyor/reconcile-pass.mjs / we:scripts/conveyor/session-reaper.mjs / we:scripts/conveyor/lease-reaper.mjs. That was false and is corrected here, because the recommendation below rested on it: none of those four invokes the dispatch operation at all. we:scripts/conveyor/tick-core.mjs imports nothing from we:scripts/operations/dispatch-lane.mjs and only EMITS a plan -- decisions.spawnBuilds -- for the judgment-layer bridge to execute; the three passes import only unrelated helpers from we:scripts/operations/dispatch-lane-io.mjs, namely defaultListAgents, normalizeHandle and prListTimeoutMs, plus one grace-period constant. The LIVE conveyor build-dispatch path is we:skills-src/conveyor/SKILL.md §3's own instruction to the main-session bridge -- fill the delivery brief, then "spawn it as one background Agent" -- i.e. the identical harness-Agent mechanism this card attributes to hand-dispatched work; and that file's line-77 @operation-home-ok marker records in its own words that routing the spawnBuilds/spawnPrepareScope halves through the declared dispatch-lane operation is still unfinished work: #3096, status open, itself blockedBy #3353, also open. we:scripts/operations/dispatch-lane.mjs has never made a live production dispatch.) So today's throughput number conflates the two, and a session-driven burst (like the one that filed this very card) inflates it in a way that says nothing about steady-state mechanical capacity -- the thing the operator actually wants to track toward the long-term goal of the interactive session disappearing entirely. Separately, we:scripts/readiness/conveyor-instrument.mjs (#2680) already has a mark-dispatch/mark-setup CLI writing a we:.conveyor/dispatch-log.json sidecar keyed by item num -- built for a DIFFERENT purpose (decomposing per-item wall-clock latency into authoring/setup/firstCi/land phases for a throughput-lever go/no-go) but CONFIRMED DEAD: no caller anywhere invokes mark-dispatch or mark-setup, and no we:.conveyor/dispatch-log.json exists on disk. Wiring we:scripts/operations/dispatch-lane.mjs's effect-apply step (we:scripts/operations/dispatch-lane-io.mjs) to stamp a per-item dispatch-origin marker WOULD, by construction, make every stamped item num conveyor-origin and every unstamped-but-resolved item origin-unknown/session-driven-by-elimination -- reusing the dead primitive's exact mechanism rather than inventing a third one -- but that by-construction argument holds only ONCE that step is on the live dispatch path, and per the correction above it is not. Hence blockedBy #3096: built as scoped BEFORE #3096 lands, the stamp would fire on zero real dispatches, every conveyor-mechanized build would go unstamped and be classified session-driven by elimination, and the resulting conveyor-only number would be a near-zero that inverts this card's whole stated purpose. FORK 0 (sequencing -- settle this first, it gates Fork 1's value): (a) BLOCK on #3096 and stamp at the single declared effect-apply seam once the conveyor really dispatches through it -- RECOMMENDED: one stamp site, no second mechanism, and #3096 is already the surviving card for exactly this routing; (b) stamp NOW at the bridge instead, having we:skills-src/conveyor/SKILL.md §3's spawn step write the marker before it spawns the Agent -- measures immediately, but puts a durable data write inside prose-driven main-session work, which is the precise class of step #3096 exists to mechanize away, and it would be torn out again when #3096 lands; (c) stamp at BOTH surfaces -- rejected, two writers of one field with no single owner, and the double-stamp/skew question it opens is not worth the interim window. FORK 1 (the design fork WITHIN option (a)): HOW is the stamp made durable enough for multi-week velocity trend analysis, not just #2680's original fine-grained recent-window latency use? (a) resurrect the we:.conveyor/dispatch-log.json sidecar as-is and have we:scripts/readiness/velocity-metrics.mjs join on it -- fastest, reuses dead code verbatim, but the sidecar is explicitly documented as gitignored/ephemeral ('a small signal, not a durable store'), so a lane-pool litter reap (we:backlog/3568) or a fresh clone could silently lose dispatch history a velocity trend depends on; (b) stamp a lightweight field directly onto the backlog item's own committed frontmatter at dispatch time (e.g. dispatchOrigin: conveyor, mirroring how dateStarted is already stamped) -- durable by construction (committed data, the same single-source-of-truth convention we:scripts/readiness/velocity-metrics.mjs already reads), costs one new optional field, absent-safe for every item filed before this lands; (c) infer origin post-hoc from session-slug or PR-metadata heuristics -- rejected outright, it fights the same no-fabricated-precision principle both #2686 and #2680 already establish in their own file headers. RECOMMENDED DEFAULT: (b), the durable frontmatter stamp -- velocity is inherently a historical-trend metric, and the repo's own state-lives-where-its-nature-dictates convention (we:docs/agent/platform-decisions.md#state-lives-where-its-nature-dictates) says durable per-item facts belong in the committed item, not a gitignored sidecar. Once ratified AND #3096 has landed, the mechanical follow-on (build-ready, no further fork) is: (1) we:scripts/operations/dispatch-lane-io.mjs stamps the marker at effect-apply, (2) we:scripts/readiness/velocity-metrics.mjs's gatherItems/rollUp gains an origin filter so --origin=conveyor reports throughput for JUST mechanically-dispatched work. Neither half may ship before #3096: until the conveyor actually dispatches through the operation, --origin=conveyor reports a near-zero that must not be read as a capacity signal. FORK 2 (a further follow-on slice, noted per the operator's own mid-session extension, NOT built now): once real conveyor-only throughput exists, forecast a queue-runway (ready-and-dispatchable queue depth divided by the measured conveyor-only dispatch rate = time until the queue runs dry) -- directly motivated by tonight's real incident, where the queue looked thin and needed manual investigation to find it was mostly stale already-done noise, not real scarcity. A naive raw-queue-length numerator would reproduce that exact confusion. we:scripts/readiness/dispatch-plan.mjs already computes the fix: its held-reason vocabulary (HELD_REASONS) already separates real capacity-bound holds (no free lane, overlaps lane-N) from non-work noise (already-done -- #3457/#3460's own age-gated ground-truth fix for exactly this incident class, blocked, needs-slice, needs-decision, unshaped-no-scope, branch-drift-blocked). RECOMMENDED DEFAULT for the runway depth definition: genuinely-dispatchable depth = launch.length + count of items held ONLY for no-free-lane/overlaps-lane-N reasons (real work blocked purely by capacity, not by noise) -- reusing we:scripts/readiness/dispatch-plan.mjs's existing classification rather than a new one. This makes Fork 2's depth question NOT a real open fork (we:dispatch-plan.mjs already draws the exact line tonight's incident needed) -- so once Fork 1 is ratified and the conveyor-only throughput denominator exists, the runway estimate (depth-count / conveyor-only items-per-day) is a small build-ready story, not a second decision. Distinct from we:backlog/3569 (the rolling-24h capacity monitor: lane utilization / queue depth / dispatch rate / heavy-admission concurrency) -- #3569 is explicitly current-state capacity, never throughput/velocity, and its own text does not claim this ground; this item is a sibling that should cross-reference #3569 (both may eventually read the same underlying dispatch-log/frontmatter signal) rather than be folded into it, since #3569's done-when is capacity-shaped and forcing velocity/runway into it would blur that.
