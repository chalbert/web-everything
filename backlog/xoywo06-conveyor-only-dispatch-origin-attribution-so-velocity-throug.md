# Conveyor-only dispatch-origin attribution, so velocity/throughput can be measured for the mechanical engine alone (and a queue-runway forecast on top)

Grounded 2026-09-07: we:scripts/readiness/velocity-metrics.mjs (#2686) already computes real throughput (points/wk, items/wk over a trailing window) plus cycle-time and WIP-split, purely from backlog dateOpened/dateStarted/dateResolved/size -- but it has NO notion of dispatch origin at all: every resolved item counts toward throughput regardless of whether its build was launched by the conveyor's own mechanical tick (we:scripts/operations/dispatch-lane.mjs, invoked ONLY by we:scripts/conveyor/tick-core.mjs, we:reconcile-pass.mjs, we:session-reaper.mjs and we:lease-reaper.mjs -- confirmed the sole caller) or hand-dispatched by an interactive session's own Agent-tool/claude-bg call (which never touches we:dispatch-lane.mjs or writes any repo-side record at all). So today's throughput number conflates the two, and a session-driven burst (like the one that filed this very card) inflates it in a way that says nothing about steady-state mechanical capacity -- the thing the operator actually wants to track toward the long-term goal of the interactive session disappearing entirely. Separately, we:scripts/readiness/conveyor-instrument.mjs (#2680) already has a mark-dispatch/mark-setup CLI writing a we:.conveyor/dispatch-log.json sidecar keyed by item num -- built for a DIFFERENT purpose (decomposing per-item wall-clock latency into authoring/setup/firstCi/land phases for a throughput-lever go/no-go) but CONFIRMED DEAD: no caller anywhere invokes mark-dispatch or mark-setup, and no we:.conveyor/dispatch-log.json exists on disk. Because we:dispatch-lane.mjs is the SOLE conveyor dispatch surface, wiring its effect-apply step (we:scripts/operations/dispatch-lane-io.mjs) to stamp a per-item dispatch-origin marker would, by construction, make every stamped item num conveyor-origin and every unstamped-but-resolved item origin-unknown/session-driven-by-elimination -- reusing the dead primitive's exact mechanism rather than inventing a third one. FORK 1 (the real design fork): HOW is the stamp made durable enough for multi-week velocity trend analysis, not just #2680's original fine-grained recent-window latency use? (a) resurrect the we:.conveyor/dispatch-log.json sidecar as-is and have we:scripts/readiness/velocity-metrics.mjs join on it -- fastest, reuses dead code verbatim, but the sidecar is explicitly documented as gitignored/ephemeral ('a small signal, not a durable store'), so a lane-pool litter reap (we:backlog/3568) or a fresh clone could silently lose dispatch history a velocity trend depends on; (b) stamp a lightweight field directly onto the backlog item's own committed frontmatter at dispatch time (e.g. dispatchOrigin: conveyor, mirroring how dateStarted is already stamped) -- durable by construction (committed data, the same single-source-of-truth convention we:scripts/readiness/velocity-metrics.mjs already reads), costs one new optional field, absent-safe for every item filed before this lands; (c) infer origin post-hoc from session-slug or PR-metadata heuristics -- rejected outright, it fights the same no-fabricated-precision principle both #2686 and #2680 already establish in their own file headers. RECOMMENDED DEFAULT: (b), the durable frontmatter stamp -- velocity is inherently a historical-trend metric, and the repo's own state-lives-where-its-nature-dictates convention (we:docs/agent/platform-decisions.md#state-lives-where-its-nature-dictates) says durable per-item facts belong in the committed item, not a gitignored sidecar. Once ratified, the mechanical follow-on (build-ready, no further fork) is: (1) we:scripts/operations/dispatch-lane-io.mjs stamps the marker at effect-apply, (2) we:scripts/readiness/velocity-metrics.mjs's gatherItems/rollUp gains an origin filter so --origin=conveyor reports throughput for JUST mechanically-dispatched work. FORK 2 (a further follow-on slice, noted per the operator's own mid-session extension, NOT built now): once real conveyor-only throughput exists, forecast a queue-runway (ready-and-dispatchable queue depth divided by the measured conveyor-only dispatch rate = time until the queue runs dry) -- directly motivated by tonight's real incident, where the queue looked thin and needed manual investigation to find it was mostly stale already-done noise, not real scarcity. A naive raw-queue-length numerator would reproduce that exact confusion. we:scripts/readiness/dispatch-plan.mjs already computes the fix: its held-reason vocabulary (HELD_REASONS) already separates real capacity-bound holds (no free lane, overlaps lane-N) from non-work noise (already-done -- #3457/#3460's own age-gated ground-truth fix for exactly this incident class, blocked, needs-slice, needs-decision, unshaped-no-scope, branch-drift-blocked). RECOMMENDED DEFAULT for the runway depth definition: genuinely-dispatchable depth = launch.length + count of items held ONLY for no-free-lane/overlaps-lane-N reasons (real work blocked purely by capacity, not by noise) -- reusing we:scripts/readiness/dispatch-plan.mjs's existing classification rather than a new one. This makes Fork 2's depth question NOT a real open fork (we:dispatch-plan.mjs already draws the exact line tonight's incident needed) -- so once Fork 1 is ratified and the conveyor-only throughput denominator exists, the runway estimate (depth-count / conveyor-only items-per-day) is a small build-ready story, not a second decision. Distinct from we:backlog/3569 (the rolling-24h capacity monitor: lane utilization / queue depth / dispatch rate / heavy-admission concurrency) -- #3569 is explicitly current-state capacity, never throughput/velocity, and its own text does not claim this ground; this item is a sibling that should cross-reference #3569 (both may eventually read the same underlying dispatch-log/frontmatter signal) rather than be folded into it, since #3569's done-when is capacity-shaped and forcing velocity/runway into it would blur that.
