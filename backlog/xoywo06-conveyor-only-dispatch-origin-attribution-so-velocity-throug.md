# Conveyor-only dispatch-origin attribution, so velocity/throughput can be measured for the mechanical engine alone (and a queue-runway forecast on top)

Grounded 2026-09-07: we:scripts/readiness/velocity-metrics.mjs (#2686) already computes real throughput (points/wk, items/wk over a trailing window) plus cycle-time and WIP-split, purely from backlog dateOpened/dateStarted/dateResolved/size -- but it has NO notion of dispatch origin at all: every resolved item counts toward throughput regardless of whether its build was launched by the conveyor's own mechanical tick or hand-dispatched by an interactive session. RE-GROUNDED 2026-09-09 (correcting this card's original premise, which claimed we:scripts/operations/dispatch-lane.mjs was the sole conveyor dispatch surface, invoked by tick-core/reconcile-pass/session-reaper/lease-reaper -- that claim was false): those two launches are TODAY THE SAME MECHANISM. we:skills-src/conveyor/SKILL.md §3 (the live conveyor spec) has the main-session bridge "Spawn ONE background delivery agent per surfaced `decisions.spawnBuilds` entry ... as one background `Agent`" -- the identical harness Agent-tool call a hand-dispatch makes, writing no repo-side origin record either way, so the mechanism itself distinguishes nothing; what distinguishes them is only whether the spawn came from the runner's surfaced decisions. And we:scripts/operations/dispatch-lane.mjs is a DECLARED operation, not a live conveyor caller: nothing under we:scripts/conveyor/ invokes its dispatch effect. The only static importer of the operation itself is we:scripts/operations/run.mjs (the generic operation runner); we:scripts/conveyor/tick-core.mjs does not import it at all (deliberately -- it mirrors the slug grammar rather than importing across the boundary, per its own header -- and only emits the JSON plan the bridge executes); we:scripts/conveyor/reconcile-pass.mjs and we:scripts/conveyor/session-reaper.mjs import only listing helpers (defaultListAgents / normalizeHandle / prListTimeoutMs) from we:scripts/operations/dispatch-lane-io.mjs; we:scripts/conveyor/lease-reaper.mjs imports only the DISPATCH_GUARD_LISTING_GRACE_MINUTES constant. Routing the conveyor's build dispatch through the declared operation is its own item, #3096 (status: open), itself blockedBy #3353 ("...then make the first live dispatch", also open) -- i.e. the operation has never made a live production build dispatch. So today's throughput number conflates the two, and a session-driven burst (like the one that filed this very card) inflates it in a way that says nothing about steady-state mechanical capacity -- the thing the operator actually wants to track toward the long-term goal of the interactive session disappearing entirely. Separately, we:scripts/readiness/conveyor-instrument.mjs (#2680) already has a mark-dispatch/mark-setup CLI writing a we:.conveyor/dispatch-log.json sidecar keyed by item num -- built for a DIFFERENT purpose (decomposing per-item wall-clock latency into authoring/setup/firstCi/land phases for a throughput-lever go/no-go) but CONFIRMED DEAD: no caller anywhere invokes mark-dispatch or mark-setup, and no we:.conveyor/dispatch-log.json exists on disk. Reusing that dead primitive's exact mechanism -- a per-item dispatch-origin marker written at dispatch time -- rather than inventing a third one is still the right move, but WHERE the marker is written is a real question the original false premise hid, and it is FORK 0, logically prior to Fork 1's durability question. Stamping at the declared operation's effect-apply step (we:scripts/operations/dispatch-lane-io.mjs) yields the desired by-construction property -- every stamped num conveyor-origin, every unstamped-but-resolved num origin-unknown/session-driven-by-elimination -- ONLY IF every conveyor dispatch actually flows through that step. Today none does, and the by-elimination reading then INVERTS: real conveyor-mechanized builds, dispatched by the bridge's Agent-tool call, go unstamped and are misclassified as session-driven, which defeats this card's entire stated purpose. Note the asymmetry that survives: the mechanical dispatch that IS live today -- the fix pass (we:scripts/conveyor/reconcile-fix-dispatch.mjs, #3438) and independent review dispatch (we:scripts/operations/review-dispatch.mjs, #3279) -- reaches the world through we:scripts/operations/dispatch-lane-io.mjs#buildAgentArgv/#defaultSpawnAgent DIRECTLY, not through the declared operation's effect-apply, so those spawn helpers are a genuinely live choke point while the operation's effect step is not; neither, however, dispatches a BUILD, which is the population velocity counts. FORK 0 (where the stamp is written): (a) sequence this behind #3096 so the declared operation really becomes the sole build-dispatch surface, then stamp at effect-apply exactly as originally scoped -- honest by construction, at the cost that this card's readiness becomes #3096's (and transitively #3353's), not its own; (b) write the stamp from the bridge itself, adding it to we:skills-src/conveyor/SKILL.md §3's spawn step -- reaches today's real builds, but a prose instruction an LLM executes is a fabricable, unenforceable stamp, the same no-fabricated-precision objection that already rejects (c) under Fork 1 below; (c) write it from the delivery agent's own brief at claim time (we:skills-src/conveyor/delivery-agent-brief.md) -- same objection, one layer down; (d) narrow the metric's ambition to the dispatch paths that already have a mechanical choke point (fix/review via the spawn helpers) and report no origin for builds -- honest, but it measures the population the operator is not asking about. RECOMMENDED DEFAULT for Fork 0: (a) -- take the honest dependency, recorded as blockedBy #3096 in this card's frontmatter, rather than ship a stamp that measures a path no production build currently takes. FORK 1 (the real design fork): HOW is the stamp made durable enough for multi-week velocity trend analysis, not just #2680's original fine-grained recent-window latency use? (a) resurrect the we:.conveyor/dispatch-log.json sidecar as-is and have we:scripts/readiness/velocity-metrics.mjs join on it -- fastest, reuses dead code verbatim, but the sidecar is explicitly documented as gitignored/ephemeral ('a small signal, not a durable store'), so a lane-pool litter reap (we:backlog/3568) or a fresh clone could silently lose dispatch history a velocity trend depends on; (b) stamp a lightweight field directly onto the backlog item's own committed frontmatter at dispatch time (e.g. dispatchOrigin: conveyor, mirroring how dateStarted is already stamped) -- durable by construction (committed data, the same single-source-of-truth convention we:scripts/readiness/velocity-metrics.mjs already reads), costs one new optional field, absent-safe for every item filed before this lands; (c) infer origin post-hoc from session-slug or PR-metadata heuristics -- rejected outright, it fights the same no-fabricated-precision principle both #2686 and #2680 already establish in their own file headers. RECOMMENDED DEFAULT: (b), the durable frontmatter stamp -- velocity is inherently a historical-trend metric, and the repo's own state-lives-where-its-nature-dictates convention (we:docs/agent/platform-decisions.md#state-lives-where-its-nature-dictates) says durable per-item facts belong in the committed item, not a gitignored sidecar. Once ratified AND #3096 has routed the conveyor's build dispatch through the declared operation (Fork 0's (a)), the mechanical follow-on (no further fork) is: (1) we:scripts/operations/dispatch-lane-io.mjs stamps the marker at effect-apply, (2) we:scripts/readiness/velocity-metrics.mjs's gatherItems/rollUp gains an origin filter so --origin=conveyor reports throughput for JUST mechanically-dispatched work. Step (2) is build-ready on its own and absent-safe (an unstamped item simply reports origin-unknown); step (1) is NOT build-ready until #3096 lands, because until then there is no live build dispatch at that step to stamp -- which is exactly why this card carries blockedBy #3096 rather than claiming build-readiness now. FORK 2 (a further follow-on slice, noted per the operator's own mid-session extension, NOT built now): once real conveyor-only throughput exists, forecast a queue-runway (ready-and-dispatchable queue depth divided by the measured conveyor-only dispatch rate = time until the queue runs dry) -- directly motivated by tonight's real incident, where the queue looked thin and needed manual investigation to find it was mostly stale already-done noise, not real scarcity. A naive raw-queue-length numerator would reproduce that exact confusion. we:scripts/readiness/dispatch-plan.mjs already computes the fix: its held-reason vocabulary (HELD_REASONS) already separates real capacity-bound holds (no free lane, overlaps lane-N) from non-work noise (already-done -- #3457/#3460's own age-gated ground-truth fix for exactly this incident class, blocked, needs-slice, needs-decision, unshaped-no-scope, branch-drift-blocked). RECOMMENDED DEFAULT for the runway depth definition: genuinely-dispatchable depth = launch.length + count of items held ONLY for no-free-lane/overlaps-lane-N reasons (real work blocked purely by capacity, not by noise) -- reusing we:scripts/readiness/dispatch-plan.mjs's existing classification rather than a new one. This makes Fork 2's depth question NOT a real open fork (we:dispatch-plan.mjs already draws the exact line tonight's incident needed) -- so once Fork 1 is ratified and the conveyor-only throughput denominator exists, the runway estimate (depth-count / conveyor-only items-per-day) is a small build-ready story, not a second decision. Distinct from we:backlog/3569 (the rolling-24h capacity monitor: lane utilization / queue depth / dispatch rate / heavy-admission concurrency) -- #3569 is explicitly current-state capacity, never throughput/velocity, and its own text does not claim this ground; this item is a sibling that should cross-reference #3569 (both may eventually read the same underlying dispatch-log/frontmatter signal) rather than be folded into it, since #3569's done-when is capacity-shaped and forcing velocity/runway into it would blur that.
