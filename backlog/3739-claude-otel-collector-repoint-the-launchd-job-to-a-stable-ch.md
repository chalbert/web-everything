# Claude OTel collector: repoint the launchd job to a stable checkout and keep its data in one shared root

PROBLEM (verified 2026-09-20): the collector launchd job points at the script path inside the primary checkout, where the file no longer exists (that checkout is far behind the prototype branch). The running process (started 2026-09-13) works only because it loaded the code earlier; any restart or reboot fails to start it. Its data goes to a checkout-local directory (claude-otel under that checkout dot-operations), so each lane clone can write a different root and a rollup silently misses lane-local data (known unfixed, noted in the collector code comments). DESIGN TO SETTLE BEFORE BUILD (strong design required): (1) WHERE THE CODE LIVES: the collector (we:scripts/operations/claude-otel-collector.mjs) exists on the prototype branch only; either graduate it to main (epic 3443 slice) or install from a dedicated stable clone that tracks the branch, as the host sampler does (we:scripts/operations/host-sampler-install.mjs is the pattern: install, uninstall, status, print-plist, plutil lint, never auto-load). (2) DATA ROOT: one shared root under the operator workspace operations directory beside the telemetry files, never per checkout; one-time merge of the existing day files with a verified line-count match and no deletion of the originals until the operator confirms. (3) NO-GAP SWAP: load the new job, confirm fresh records, then unload the old process; the exporter retries, so the swap must not drop more than one export interval; the operator approves the swap, the build never stops the running collector. (4) SAFETY: receiver stays on localhost, numeric counters only, never persist the logs channel or prompt content (existing guard); the missing authentication on the local receiver is an accepted single-operator risk, re-open it if this ever serves more than one operator. ACCEPTANCE: a status command reports script exists, process matches the plist, newest record age under a stated bound and the data root; a test lints the plist and fails when the script path is absent; after the swap new records land in the shared root.

## Design review (jury, 2026-09-20, careLevel elevated)

Run wf_de7a8ca4-29f: a seven-lens panel (correctness, security, simplicity, standards-conformance, claim-accuracy, root-cause, completeness), one juror per lens. Round 1 reviewed the design above and reduced to `changes` (five lenses prevention-outstanding, two changes; panel cost $0.48). An editor revised the design; round 2 re-reviewed the revision. The run's own round-2 reduce returned needs-human with every lens unknown because the launcher failed to relay the panel result (see backlog 3741), so there is NO round-2 verdict; the round-2 panels themselves ran (two runs, $0.58 and $0.61) and their findings survive only in two tool-result relay files. The revision is not merged into this card: the text above is the original design, and the editor's revision sits in the run journal. Build from the findings below, not from the original text alone.

### Findings that stand against the design above (round 1; findings 1 and 5 were raised by all seven lenses, the rest by several)

1. **The swap order is impossible.** Load-new-then-unload-old cannot work: the old process holds port 4318 and every session exports to that fixed port, so a second collector fails to bind (address in use). Real sequence is stop old, start new, with a bounded gap; prove it with a dry run on another port (needs a port override that the service plist must never carry); the status command must report which PID owns 4318. Confirmed in code: the default port is 4318 (we:scripts/operations/claude-otel-collector.mjs).
2. **No rollback path.** The old process is the only working copy of the collector (its script no longer exists at the plist path), so once stopped nothing can restart it and a failed new job leaves capture down. Needs: preserve the old plist and recover the old code from history before stopping anything, an abort condition, a timebox. Round 2 sharpened it: the recovered old code resolves its root relative to its own checkout and may not be able to write to the shared root, so "restart the old script" must say where it writes and how.
3. **The data root is never resolved or repointed for readers.** The design moves the root but does not say how the collector or the readers (rollup, status, lane-clone tools) learn it. Wanted: ONE shared resolver module; a plist environment override that fails closed when unset in service mode; a test that checkout-relative defaults are gone. Round 2 found the remaining hole: readers run from shells and lane clones with no plist environment, and "service mode" is not defined, so reader-mode behaviour when the override is unset must be stated. Checked in code: the branch version already has an override (OPERATION_CLAUDE_OTEL_DIR) with a default relative to the script location (we:scripts/operations/claude-otel-collector.mjs, claudeOtelDir); whether the process running since 2026-09-13 has the override is NOT known (round-2 jurors assumed it does not).
4. **The merge races the live writer.** The old process keeps appending to the old day files until it is stopped, so a line-count match taken while it runs is stale; only the primary checkout's ~5,400 lines are named while lane clones may hold their own roots. Wanted: enumerate every lane root, stop the writer first, an idempotent dedup merge with a manifest of per-source hashes, a final delta merge after the writer stops. Round 2: whole-record dedup can undercount, because delta exports of identical values are legitimately identical; state whether dedup is across sources or within one, and how the final merge writes into a day file the new collector is already appending to.
5. **Point 1 is undecided and a branch-tracking clone recreates the root cause.** A launchd job pointing at a mutable checkout that follows a moving branch is the incident again (rebase, rename, delete, stale clone). Wanted: prefer graduating the collector to main; if a copy, pin a named commit or copy the bytes (from the git object, not a working tree), record a manifest, use an absolute node path, and make status compare the hash of the RUNNING code. Round 2 found that a hash of the file on disk still cannot show what the live process loaded (the exact failure that started this story); compare against the process start time and the install time, or restart after every install.
6. **Acceptance is weak.** The "newest record age under a stated bound" names no bound and an idle machine looks unhealthy (status must know whether a session is active, and round 2 notes the design never says how); the plist lint test must run on the generated plist, not the operator's installed file, or it is skipped in CI, and the status command carries the installed-file check; nothing alerts when the job is down (recurring check chosen at implementation, with no acceptance test that the wiring exists). Round 2 adds: the plist must assert RunAtLoad, KeepAlive with a throttle, absolute log paths outside any checkout, a working directory.
7. **Security and PII hardening.** Bind 127.0.0.1 explicitly: confirmed in code that the server listens with no host argument (server.listen(port, callback)), which binds every interface, so the "stays on localhost" claim is false today. Also: directory mode 0700 and file mode 0600, the root ignored by git and excluded from sync and backup, Host and Origin checks, content-type and body-size limits, a numeric-attribute allowlist rather than a denylist, a test that a logs-channel payload is dropped, hash or drop the email at ingest. Confirmed in code that user.email and session id are kept as attributes on stored records. Round 2: ingest-side scrubbing does not cover the historic plaintext copied by the merge, and it changes record format mid-migration, breaking whole-record dedup; the follow-up deletion of originals has no owner or gate; real exporters may send a charset on the content type or compress the body, which new guards would reject on cutover day, so validate against a real payload, not only a synthetic record.
8. **Restart state and exporter retry semantics are unverified.** Delta temporality means the collector keeps no running totals (confirmed in the code header: it never diffs against a remembered baseline), so the restart-state worry is smaller than round 1 feared. Whether the exporter retries or drops a batch sent during the gap is NOT known; if it drops, the gap loses usage permanently, so measure the gap and state the loss bound rather than promising "one export interval".
9. **Scope.** Round 2 (simplicity and correctness) says the story bundles too much: a generic swap subcommand with a stubbed launchctl harness, manifest merge, PII policy, receiver hardening, doctor wiring. Consider splitting the safe core (pinned install, absolute root, plist lifecycle keys, stop-then-start swap with rollback) from the hardening and the merge tool.

### Findings that rest on assumptions the jurors could not check

- That the plist sets KeepAlive (round 1 said "if KeepAlive is set"); the host-sampler installer pattern does set it, this job's plist was not read.
- That the plist's node path comes from a version manager and can vanish (the installer pattern records the node that ran it, we:scripts/operations/host-sampler-install.mjs; which node the live job uses was not read).
- That the exporter drops failed batches instead of retrying (jurors: "commonly"; not verified against the docs or the exporter).
- That the shared root would be git-tracked or synced: the checkout-local root is gitignored (confirmed in the repo ignore file), and the new shared root sits outside any repository, so this is a hazard to rule out, not a fact.
- Any reading of the running process (its start time, the address it bound) was not made; the jurors reasoned from the card text.
