# Choose the dispatch worker's model from one checked-in routing table by kind, and refuse a hand-set model that carries no reason

A dispatched worker's model comes only from the process-wide env var WE_DISPATCH_AGENT_ARGS: no table, no validation, no recorded reason, so a caller hand-picks it (on 2026-09-21 most of ~40 workers were set to opus by hand against the Sonnet-default standard, and nothing stopped it). The router already computes a tier and records it in the run record, but no spawn code reads it. Make one checked-in table (kind, taskType, scope facts to tier) decide the model at the shared spawn point, and refuse a hand-set model that carries no reason.

**Prototype work (epic #3383).** Build it on `lane/mechanical-dispatcher` and commit there; there is no PR (the prototype branch is not landed through the drain; slices graduate through #3443). The card file itself lives on `main`. Every `we:` path and line below is on `origin/lane/mechanical-dispatcher` at `5ab89f87b`, verified 2026-09-21; none of these files exists on `main`.

**Why it is fixed on the operation, not worked around.** The operator's rule (2026-09-22): when a declared operation has a limitation, fix the operation; that is what the prototype is for. A hand-set model on every dispatch was a workaround the operation allowed.

## FOUND (2026-09-21, each claim checked in the code)

- **The model has one carrier, and it has no checks.** we:scripts/operations/dispatch-task.mjs:304 says "A worker model rides `WE_DISPATCH_AGENT_ARGS`". we:scripts/operations/run.mjs:301 reads that variable for the whole process (`createDispatchTaskSinks({ extraArgs: agentArgsFromEnv() })`; we:scripts/operations/run.mjs:267 does the same for `dispatch-lane`). `agentArgsFromEnv` (we:scripts/operations/dispatch-lane-io.mjs:901-910) checks only that the value is a JSON array of strings. we:scripts/operations/dispatch-task-io.mjs:133-137 puts those args first in the argv. A pinned test asserts the pass-through as a feature (we:scripts/operations/__tests__/dispatch-task.test.mjs:301-307). No table, no validation, no reason.
- **Every spawn shares one argv builder.** `buildAgentArgv` (we:scripts/operations/dispatch-lane-io.mjs:1456-1471) just appends `extraArgs`. Its callers: we:scripts/operations/dispatch-lane-io.mjs:1343 (the provider behind both `dispatch-lane` and `dispatch-task`), we:scripts/operations/review-dispatch.mjs:467 and we:scripts/conveyor/reconcile-fix-dispatch.mjs:395,506. Those last two read the same env variable (we:scripts/operations/review-dispatch.mjs:574, we:scripts/conveyor/reconcile-fix-dispatch.mjs:615). we:scripts/operations/explore-io.mjs:405 carries a second copy of the parser. So a model check at `buildAgentArgv` covers every Claude dispatch; a check inside `dispatch-task` alone would cover one.
- **A tier is already computed and then dropped.** `decideDispatchRoute` returns `tier` and `model` (we:scripts/lib/dispatch-contracts.mjs:857-858), taken from `selectProvider`'s Claude-tier step (we:scripts/lib/provider-routing.mjs:545-579) and mapped to an id by `CLAUDE_NATIVE_MODEL_BY_TIER` (we:scripts/lib/dispatch-contracts.mjs:481). A search of `scripts/` for a reader of `routing.model` or `routing.tier` finds none: the spawn never uses it. we:scripts/operations/dispatch-lane-io.mjs:1283-1288 instead re-reads the model out of the env args, to record it as `supervisorModel`. So the run record says what the operator typed, not what the criteria chose.
- **That computed tier is not the standard, so wiring it in as is would make things worse.** Run on the prototype tip today: a size-13 `build` and an UNSIZED `build` both return `tier: opus` (the step at we:scripts/lib/provider-routing.mjs:565 makes any card over 500 lines Opus, and `SIZE_TO_ESTIMATED_LOC` at we:scripts/lib/dispatch-contracts.mjs:80 reads size 13 and an unsized card as 900 lines; `estimatedLocForSize` is at we:scripts/lib/dispatch-contracts.mjs:737-742). A size-5 `build` and a conflict `fix` return sonnet. A `build` scoped to we:docs/agent/platform-decisions.md returns opus. Role kinds (`review`, `prepare-decision`) return no tier at all (the role path of `decideDispatchRoute`, we:scripts/lib/dispatch-contracts.mjs:801-823). So the router's Opus criteria (size and file count, untestable acceptance, `triage-research`) differ from the operator's list below.
- **A third table exists and has no caller.** `STORY_KIND_RUNGS` (we:scripts/lib/dispatch-contracts.mjs:89): `prepare: sonnet`, `prepare-decision: opus`, `investigate: opus`, `fix: sonnet`, `ci-heal: sonnet`, used only by the `story` stage, which nothing calls yet (#3801 follow-up 1). Its `investigate: opus` row differs from the operator's list.
- **The repo's written standard has two voices.** we:agent-memory-src/workflow-lane-model-policy.md and we:docs/agent/backlog-workflow.md#model-routing say Sonnet by default, Opus for judgment-shaped work, never Fable for execution. The second one also puts "review a diff" and "red-team" on the Opus rung, for the interactive loop's own sub-agent spawns. The operator's 2026-09-22 routing rule (kept in the orchestrating session's handoff rules file, outside this repository) is narrower and later: Sonnet for filing and copying cards, reviews, reapers, mechanical builds and ports, doc corrections and data refreshes; Opus ONLY for preparing a decision's forks, rewording statute or rule text, security-critical fixes, and wide-blast-radius dispatch machinery; escalate a Sonnet worker to Opus only after it reports it could not do the job. The statute [delegation-trial-record-graduation](/docs/agent/platform-decisions.md#delegation-trial-record-graduation), "Reach", says mechanical routing binds the mechanical dispatch path only, so the operator's list governs this table and the interactive loop's own rule is untouched.

## The build (settled here; nothing below waits on a ruling)

**1. One table, one function.** Add one checked-in table and ONE pure function, `workerTierFor({ kind, taskType, scopePaths, tags })`, that returns `{ tier, reason }` with `tier` one of `sonnet` or `opus` only. It lives in we:scripts/lib/provider-routing.mjs, replacing the Claude-tier criteria at lines 545-579 in place, and is read through we:scripts/lib/dispatch-task-type.mjs (which supplies the kind and the taskType). `STORY_KIND_RUNGS` is folded into it, not kept beside it, and `routeDispatch`'s `tier` and `model` become its answer (the id still comes from `CLAUDE_NATIVE_MODEL_BY_TIER`; no new id map). Rows, from the operator's rule:

| Dispatch fact | Tier | Reason recorded |
| --- | --- | --- |
| any kind not listed below: `build`, `fix`, `ci-heal`, `review`, `prepare`, `investigate`, and every free `dispatch-task` label (filing, verify-first, close-out, reaper, data refresh, ...) | `sonnet` | the standard's default |
| kind `prepare-decision`, or taskType `architectural-decision` | `opus` | preparing a decision's forks is judgment |
| scope names a path where `isStatuteTierPath` is true (anything under `docs/agent/`), or kind `statute-wording` | `opus` | rewording statute or rule text |
| kind `security-fix`, or card tag `security` | `opus` | a security-critical fix |
| scope names a path in a short frozen `DISPATCH_MACHINERY_PATHS` list (initially the dispatch operations and libraries: we:scripts/operations/dispatch-lane-io.mjs, we:scripts/operations/dispatch-task.mjs, we:scripts/lib/dispatch-contracts.mjs, we:scripts/lib/provider-routing.mjs, we:scripts/conveyor/tick-core.mjs), or kind `dispatch-machinery` | `opus` | wide-blast-radius dispatch machinery |

Rows that CHANGE, named so a reviewer sees them: the size and file-count Opus trigger (over 8 files or 500 lines) and `acceptanceTestable: false` stop forcing Opus, so a size-13 or unsized `build` is `sonnet`; `triage-research` and `investigate` stop forcing Opus; `haiku` is not a table output. A raise-only fact (a statute path, a machinery path, a listed kind) can only move a dispatch up, never down. `selectProvider` stays advisory for an interactive session, as #3798 says; its Claude-tier step now calls the same function, so the criteria exist once. For a `dispatch-task` brief there is no scope, so the facts are the caller's declared `--kind`, and the scope of `--item` when one is given. An unlisted label is `sonnet`, never a refusal: refusing would stop the ad hoc briefs that epic #3643 exists to give a kind.

**2. The model is applied at the shared spawn point.** `buildAgentArgv` takes the table's decision, emits exactly one `--model <id>`, and refuses a `--model`, `-m` or `--model=` left in `extraArgs` unless the decision says it is an override with a reason. we:scripts/operations/dispatch-task-io.mjs and we:scripts/operations/dispatch-lane-io.mjs pass the decision in; `review-dispatch` and `reconcile-fix-dispatch` get the table's answer through the same builder (the resume path, a bare `--resume`, carries no model flag and is unchanged).

**3. An override needs a reason.** `WE_DISPATCH_AGENT_ARGS` stays as the carrier of a hand-set `--model`, and stays the only way to set one, but it is honored only when the call also carries `--modelReason=<text>` (an input on `dispatch-task` and `dispatch-lane`; the name avoids `model`, which the command-line adapter reserves, we:scripts/operations/dispatch-task.mjs:303-305). A `--model` in the env with no reason is REFUSED before any session exists, with a reason that names the rule. A `--modelReason` with no hand-set model is refused too (a reason for nothing). A model name that resolves to Fable is refused even with a reason. This is the shape #3801 Fork 5 ruled for the provider override, applied to the model: an explicit, per-dispatch, recorded input with a required reason. A `dispatch-lane` call is one per item, so the reason is per item; no new card field is added (Fork 5's `deliveryAgent:` marker names a vendor, not a model, and a new frontmatter field would need a `check:standards` schema change).

**4. The run record shows the choice.** The `dispatch` block of the run record (we:scripts/operations/dispatch-lane-io.mjs:1289-1310, we:scripts/operations/dispatch-task-io.mjs:158-162) gets one `workerModel` field beside `routedProvider` and `executedProvider`: `{ name, tier, source: 'table' | 'override', tableTier, reason }`. `supervisorModel` is now read from it, not re-parsed from the env args.

**Model for building this card: Opus.** It edits `buildAgentArgv`, the one argv builder every Claude dispatch passes through, which is the wide-blast-radius dispatch machinery row above. Reason recorded here, per the same rule.

## Graduated to main by #3906 (2026-09-26)

unreasoned hand-set `--model`/`-m`/`--model=` (and any Fable model), and the run record's in-flight `dispatch`
block carries `workerModel` `{name, tier, source, tableTier, reason}`; `dispatch-lane` has the `modelReason`
input. Role kinds (prepare, prepare-decision, investigate) also get their table tier's model on `dispatch-lane`
(`workerModelTable`). The `dispatch-task` half graduates with #3903. Live dry-run over the queue (25 items x 6
kinds): every route Claude; build/fix/ci-heal/prepare/investigate spawn with `--model sonnet`, prepare-decision
and a docs/agent-scoped item with `--model opus`. The spawn flag is the tier's CLI ALIAS, not the pinned id the
routing record carries (`claude-opus-5` would be older than today's Opus 5.5), so a worker is never downgraded.
