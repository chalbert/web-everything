# Lane release never resets the tree — known scratch litter accumulates until the whole pool is unacquirable

Live-observed 2026-09-07: 46 of 48 we:.lanes/web-everything lanes were simultaneously DIRTY (untracked scratch files: we:.commit-msg.txt, we:.pr-body.md, we:.pr-body.txt, review-*-output.json, commit-msg-fix-*.txt), the other 2 clean-but-1-commit-ahead — the ENTIRE pool read 0 acquirable at once, and node we:scripts/readiness/dispatch-plan.mjs --json showed 0 launch / 71 held / 0 free lane(s) with 34 queued items starved on 'no free lane' as a direct consequence. Root cause: we:scripts/lane-pool.mjs's cmdRelease only rmSync()s the lease marker — it never resets or cleans the tree — while we:skills-src/conveyor/delivery-agent-brief.md:267 explicitly instructs every delivery agent to write its scratch files (e.g. we:.commit-msg.txt) INSIDE the lane. Auto-pick's dirty/ahead refusal in we:scripts/lane-pool.mjs (laneDirtyOrAhead, chooseFreeLane) is deliberate and correct — it protects real uncommitted work per the documented lane-11 incident (#3390) — but nothing distinguishes known-safe litter from real work, and no periodic mechanical pass (we:skills-src/conveyor/runner.mjs's makeCliMechanicalPasses has no such pass; we:scripts/conveyor/tick-core.mjs never calls lane-pool refresh/provision) ever reclaims it. The pool therefore degrades monotonically toward zero acquirable lanes as sessions complete and release without ever being force-refreshed.

**Re-confirmed live 2026-09-07 while landing this very card**: acquiring a lane for this item's own edit hit "no free lane in pool web-everything (50 all held/dirty)" — 46/50 dirty, 0 free, the identical failure mode this card describes, one tick later. The root cause is not hypothetical or fading with time; it recurs every session.

## Scope of the fix — MANDATED, not an "e.g." — two halves, both required

The original draft of this card offered the release-time fix and a periodic pass as an "and/or" open implementation choice. Re-scoped per operator direction: **both halves are required**, because they cover different failure windows — a release-time-only fix does nothing for litter that predates the fix or that accumulates through any path other than a normal release (an aborted session, a killed agent, a manual abandonment), and a periodic-pass-only fix leaves the pool degraded between ticks with no reason to stay clean by construction.

1. **Release-time fix.** `cmdRelease` (we:scripts/lane-pool.mjs), before it `rmSync()`s the lease marker, git-cleans a small **named allowlist** of known-safe scratch patterns from the lane's working tree: we:.commit-msg.txt, we:.pr-body.md, we:.pr-body.txt, we:review-*-output.json, we:commit-msg-fix-*.txt (the exact live-observed set above; extend the list, don't loosen the mechanism, if another pattern is found later). The allowlist must be an exported, named constant (mirroring we:scripts/conveyor/tick-core.mjs's `DEFAULT_*` convention) so we:skills-src/conveyor/delivery-agent-brief.md and this cleanup step can be grepped back to the same source of truth. **Never a blanket `git clean -fdx` or `reset --hard`** — those already exist elsewhere in we:scripts/lane-pool.mjs guarded by `laneDirtyOrAhead`/the #2267 data-loss guard, and this fix must not weaken that guard. A tracked-file modification, or any untracked file NOT matching the allowlist, is left exactly as `laneDirtyOrAhead` sees it today (still dirty, still correctly refused by auto-pick) — this fix only shrinks the false-positive "dirty" set, it never widens what counts as safe to discard.
2. **A standing periodic lane-pool-health pass — we:scripts/conveyor/lane-pool-health-watch.mjs** — built to the SAME structural template as we:scripts/conveyor/duplicate-pr-watch.mjs (pure-core/IO-shell split; wired into we:skills-src/conveyor/runner.mjs's `makeCliMechanicalPasses` beside it — no new cron/daemon). Each tick: reads the live pool status, and for every **unleased** lane whose ENTIRE `git status --porcelain` output matches only the same named allowlist from (1) — reused via a single shared function, never re-derived — reaps it (identical cleanup, not a second implementation). This is the ongoing half: litter that accumulated before this fix landed, or through any path other than release, gets reclaimed on the next tick rather than sitting inert until someone happens to re-release that lane. The pass also reports current pool health (acquirable / dirty / leased counts) as its own `--dry-run` output, so a human or another mechanical pass can see pool pressure without re-deriving it — this is a plain status line, not the historical rolling-window artifact (see *Relationship to #3569* below, that is a different deliverable). This pass is ACTION (auto-reap), not detect-only — unlike we:scripts/conveyor/duplicate-pr-watch.mjs's alert-only stance — because "does this lane's dirty state match ONLY the named allowlist" is a deterministic, allowlist-scoped classification with no content judgment involved, the same reasoning we:backlog/3562-a-standing-mechanical-pass-keeps-the-5-highest-leverage-open.md point 4 already uses to justify its own pass being action rather than alert-only.
3. **Config knob — the pass's on/off switch is config, never hardcoded** — `WE_LANE_POOL_HEALTH_WATCH_DISABLED`, a presence-checked boolean-flag env var (mirroring we:scripts/conveyor/queue.mjs:63's `CONVEYOR_NO_KIND_CHECK` convention, the SAME convention #3562's own `WE_DECISION_DOCKET_WATCH_DISABLED` already established) — checked first in the pass's own entrypoint so it degrades to a no-op tick with no change needed to `makeCliMechanicalPasses` itself.

## Relationship to we:backlog/3569-a-rolling-24h-delivery-capacity-monitor-artifact-lane-utiliz.md — complementary, not the same job, no third item needed

#3569 is a **passive, historical** rolling-24h Artifact dashboard (lane utilization %, queue depth, dispatch rate, heavy-admission concurrency) for human/operator visibility over time — its own card already lists we:scripts/lane-pool.mjs in scope as one of several data sources it reads, and explicitly says no periodic snapshot of lane-pool state exists anywhere today, which is true. This item's lane-pool-health-watch pass is an **active, point-in-time** mechanical remediation pass — it reaps known-safe litter every tick and reports the CURRENT pool health, it does not persist a time series or render a chart. The two are not duplicative and this item does not attempt #3569's job: once #3569 is built, it MAY read this pass's per-tick health snapshot as one input for its "lane utilization" tile (cheaper than re-deriving pool status itself), but it is not blocked by this item and can equally derive its own snapshot independently — that choice is #3569's own to make when it is built. This item's pass answers "is the pool healthy right now, and did we just fix what we could," #3569 answers "how has pool health trended over the last 24 hours" — genuinely different questions, one mechanical/corrective, one observational/historical. No third item is needed to bridge them; a one-line cross-reference in each card (this one, and the matching note added to #3569 below) is enough.
