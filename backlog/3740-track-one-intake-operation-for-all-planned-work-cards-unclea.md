# track: one intake operation for all planned work (cards uncleared, explicit kind, idempotent, safe by default)

GOAL (operator, 2026-09-20): planned work has exactly two sources, filed backlog cards and the epic 3383 tracker, and every source that produces planned work (worker result owed lists, the orchestrator handoff, wip findings, the learnings pool, escalation packets) writes through ONE mechanised operation. Today items leaked into the handoff and result files and the operator found them by accident. This design was reviewed by a 7-juror jury at low care (verdict prevention-outstanding, escalated, 40 findings, the fixes below are its outcome); this epic must be SLICED and each slice design-reviewed before any build. DESIGN. (1) ROUTING BY EXPLICIT KIND: every intake line declares fix, build, decide or note; the tool never infers it; a missing or ambiguous kind defaults to a card (over-filing is cheaper than losing work) and is flagged. Cards go through we:scripts/operations/file-item.mjs; notes go through we:scripts/prototype-tracker.mjs append-note and may only reference card ids, never carry an owed list; append-note gets a lint that rejects or converts a free-text owed list. (2) SAFETY, HARD FROM DAY ONE: file-item clears a card for the conveyor, so track files every card from non-operator provenance uncleared, cleared only by an operator or orchestrator decision, with a test that a tracked-only card is not conveyor-eligible; a strict one-line schema (length cap, allowed charset, no frontmatter delimiters, provenance set from the real file path never from content); a secret scan over each item that fails the whole batch; only a one-line summary plus a reference to the source is carried, never the raw body. (3) IDEMPOTENCY: each line is keyed by source file plus line hash recorded in the card; the resulting card id is written back into the source; duplicate detection uses we:scripts/capability-search.mjs only to WARN and LINK, never to drop; the batch is atomic or resumable and ordered so a retry is safe; the shared tracker tail has a stated merge strategy for concurrent runs. (4) LANDING AND IDS: one pull request per intake run needs a small additive stage-only flag on file-item (so the wrapper is a wrapper plus that flag, not pure); ids are assigned at land, so until then the handoff holds the provisional key and track rewrites it to the number at land; a pending-intake ledger survives until the PR lands. (5) COVERAGE: a per-source table (trigger, input form, enforcement level) for worker Owed blocks, handoff, wip findings, learnings and escalation packets; the one-time FIRST step is a backfill sweep of the current handoff, tracker owed lists and unread result files. (6) ENFORCEMENT: safety checks and id-less handoff lines are hard from day one; the worker Owed block starts soft (warn plus a wip count) with a numeric hardening rule (N clean intakes with a warning rate under X percent) and a named owner, filed as a dated backlog item. (7) VISIBILITY: wip shows the top few planned items and a separate view lists the full unified list (card 3736). SLICES TO PROPOSE ON /slice: read-only reconciler (track check), the file-item stage-only flag, the ingest adapters per source, the safety layer, the backfill sweep, the append-note lint, the hardening item. ACCEPTANCE: each slice has an executable check; the epic is done when a re-run over every source files nothing twice, no tracker note carries an owed list, and no card from non-operator provenance is conveyor-eligible.
