# Open-item WIP limit from build to merge, separate from concurrent builds

`we:scripts/conveyor/build-dispatch-policy.mjs#BUILD_DISPATCH_POLICY.maxConcurrentBuilds` (coded default `3`; live running value reportedly `5` — this card's first task confirms which, see Risks) counts only builds actively IN FLIGHT. The instant a build opens its PR, its claim/run-record evidence clears and the slot frees, while delivered-but-not-yet-merged PRs pile up in review/fix/CI — more conflicts, more fix rounds, more re-reviews, wasted tokens. **Rule:** cap OPEN ITEMS — from build start until merge (builds in flight + open PRs from delivered cards) — separately from the smaller concurrent-BUILDS cap that only bounds machine load.

## What "open item" means, precisely

An open item is one backlog card with either (a) durable in-flight build evidence, or (b) an open PR that DELIVERS it (`we:scripts/conveyor/build-dispatch-policy.mjs#prDeliversNum`, already matching a PR's `headRefName` against the `lane/<num>[attempt]-<slug>` delivery-ref shape). Both conditions can be true briefly (a build finishes and opens its PR before the claim/run-record clears) — that must count as ONE open item, not two, so the counter is the SIZE OF THE UNION of `{inFlight nums} ∪ {nums delivered by an open PR}`, not a sum.

**Codex review correction (folded 2026-09-28): there are TWO differently-computed `inFlight` values in `we:skills-src/conveyor/build-dispatch-daemon.mjs`'s `dryRun`, and this card's union must be built from the RIGHT one, named precisely, not assumed by the name alone.** (1) A raw local `inFlight` — `listBuildDispatchClaims()` + run-store rows, undeduplicated against delivered PRs — built solely to feed INTO `planBuildDispatch` as its `inFlight` argument. (2) `tick.plan.inFlight` — the TICK CORE's own already-filtered/deduped in-flight answer, used only for the dry-run REPORT's display line, which the Codex review confirmed already excludes items a PR has taken over. The new `maxOpenItems` union belongs INSIDE `planBuildDispatch`'s own pure core (`we:scripts/conveyor/build-dispatch-policy.mjs`), built from the SAME raw `(inFlight, openPrs)` arguments that function already receives (its existing `cap`/`landing-freeze`/`scope-vs-open-prs` rules already read exactly these two inputs) — never from `tick.plan.inFlight`, which is a display-only derivative computed elsewhere. This is cheap and requires no new data source; it is a correction to WHICH existing value feeds the union, not a new lookup.

**Repair work does NOT add an item.** A fix round, a CI-heal, or a conflict-resolution pass all operate on a PR that ALREADY counts (it delivers a num already in the open-items set) — they never open a second PR for the same item, so the union above already gets this right for free: `prDeliversNum` matches on the delivery ref, and a fix/heal/conflict-resolution branch is a commit onto that SAME PR, not a new one. No extra bookkeeping needed to exclude repair work; it is excluded by construction because it was never counted as a second item.

**Items waiting on the human COUNT — this is deliberate pressure.** A PR carrying `review:human` (the label `we:scripts/review-set-label.mjs` already tracks as the one tier a machine may never clear, per its own `INVARIANT 2`) is still an open PR delivering a num, so it stays inside the count. The cap does not special-case it away: a human-review backlog is exactly the kind of pressure that should make the builder stop opening MORE work, not a reason to look past it.

## Scope

- `we:scripts/conveyor/build-dispatch-policy.mjs` — add the new cap as policy data (a new `maxOpenItems` field, default proposed ~7, alongside the existing `maxConcurrentBuilds` (3) and `maxOpenPrs` (12)) and a new hold rule in `planBuildDispatch` computing the union above; **generalize or replace** the existing `maxOpenPrs`-based landing-freeze rule (`if (openPrs.length > policy.maxOpenPrs) freezeReasons.push(...)`) — today's `maxOpenPrs` counts EVERY open PR including ones this repo's own PRs that are not build deliveries (need to confirm against live data whether that ever differs from delivered-item PRs; if it doesn't in practice, `maxOpenPrs` folds into `maxOpenItems` and is retired rather than kept as a second, redundant threshold — a build-time call, not a design fork, but the two must not silently diverge if kept separate).
- `we:skills-src/conveyor/build-dispatch-daemon.mjs` — thread a `--max-open-items=N` CLI flag (mirroring the existing `--max-concurrent`/`--max-open-prs` pattern in `policyFrom`), and print the new counter in both the dry-run report (`report.policy`, the `w(...)` summary lines) and the live daemon's own status line — "the plan/wip views show the counter" per the operator's own framing.
- Both files' existing tests, extended rather than replaced — `planBuildDispatch`'s pure core is already unit-tested against synthetic `candidates`/`inFlight`/`openPrs` fixtures in `we:scripts/conveyor/__tests__/build-dispatch-policy.test.mjs`, and the daemon's CLI wiring in `we:skills-src/conveyor/__tests__/build-dispatch-daemon.test.mjs`.

## Risks

- **[Codex-found, blocker] Durable claims are NOT equivalent to a currently-running build — the union can hold "phantom" WIP for hours.** Confirmed by reading `we:skills-src/conveyor/build-dispatch-daemon.mjs#runBuildDispatchTick` (line ~124): a claim is retired when its PR delivers the item, or via an immediate-dispatch-failure path — but a build that launches successfully and later fails WITHOUT ever opening a PR has no terminal-outcome retirement in that function. Its claim survives until `we:scripts/conveyor/build-dispatch-claim.mjs`'s own 240-minute TTL (line 29) expires. So the union this card proposes is not exact — it can overcount by up to that TTL whenever a build dies silently. **Design decision (folded from the finding, not deferred):** the cap is a SOFT high-water mark meant to stop pile-up, not a hard safety invariant (nothing breaks if it is briefly off by one or two) — so rather than build new claim-retirement machinery in this card (out of scope, and a bigger change than a WIP counter warrants), this card explicitly accepts TTL-bounded staleness as a stated, known limit, AND adds one cheap check as its own first-class task: confirm whether `we:scripts/conveyor/build-dispatch-claim.mjs` already has (or could cheaply gain) a "release on detected terminal failure" path that today's `maxConcurrentBuilds` cap simply never needed because it re-checks capacity every tick regardless of a stale claim's presence; if such a hook already exists or is trivial, wire it (it improves BOTH caps, not just this card's); if not, ship with the stated 240-minute bound and let the proof plan show the bound in practice, not hide it.
- **[Codex-found, major] The cap must decrement WITHIN one planning pass, not just gate on the pre-tick snapshot.** `we:scripts/conveyor/build-dispatch-policy.mjs#planBuildDispatch`'s EXISTING `cap` rule already decrements `slots` as each candidate is admitted in its per-tick loop (line ~181-206) — a single static check against the snapshot at the top of the tick would wrongly admit multiple candidates in one pass once their combined count crosses `maxOpenItems`. The new `maxOpenItems` hold rule must decrement its own running open-items count the SAME way, inside the SAME loop, as each candidate is picked — not as a one-time gate before the loop starts. This is a concrete implementation requirement, not a design fork, and its own test case is added below (previously missing: the original test plan only covered an already-full cap, never the "admits some but not all in one tick" boundary).
- **`maxOpenPrs` (12) vs the new `maxOpenItems` (~7) can disagree.** If a PR is open but does NOT deliver any tracked backlog item (a hotfix, a manual PR, a doc change), it counts toward `maxOpenPrs` today but would NOT count toward `maxOpenItems`. Keeping both thresholds without reconciling what each is FOR risks two silently-inconsistent caps; the scope above calls for confirming (from live `openPrs` data) whether this population is large enough to matter, and either keeping both with a documented distinct purpose or retiring the redundant one.
- **Picking `~7` for `maxOpenItems` without live data first.** The operator's "default ~7, configurable in the policy data" is a starting point, not a measured number — this card's own proof plan (below) is exactly how a live number gets validated before it is trusted, and the value stays overridable via a flag/policy field precisely because it may need tuning after the first week of real traffic.
- **Race between the union's two data sources.** The raw `inFlight` (claims + run-store) and `openPrs` (a live `gh` fetch) are read at slightly different times within one tick; a build that finishes and opens its PR in that gap could theoretically be missed by both reads in one single tick. Low-stakes (worst case: one tick undercounts by one item, corrected next tick) and not worth a cross-read lock — stated so a build session does not over-engineer a fix for a single-tick blip.

## Test plan (each fails before the fix)

1. `we:scripts/conveyor/__tests__/build-dispatch-policy.test.mjs`: `planBuildDispatch` holds a new candidate under a `wip-cap`-style rule (naming convention matches the existing `cap`/`landing-freeze`/`scope-vs-open-prs` rule ids) once `{inFlight ∪ delivered-by-open-PR}` reaches `maxOpenItems`, even when `maxConcurrentBuilds` still has a free slot; **the boundary case Codex's review found missing:** with, e.g., 6 open items, a cap of 7, and 3 free build slots, offering 3 fresh candidates in ONE tick admits only 1 (the count that fits under the cap), not all 3 — proving the new rule decrements within the loop like the existing `cap` rule already does, not just against the pre-tick snapshot; a build whose OWN PR is already open and counted is not double-counted if its claim also still shows in-flight (the union, not a sum); a PR carrying `review:human` still counts (no special-case exclusion); a fix/CI-heal/conflict-resolution commit onto an EXISTING open PR does not increment the count a second time (proven via a fixture where `inFlight`/`openPrs` are unchanged across two ticks despite a repair happening).
