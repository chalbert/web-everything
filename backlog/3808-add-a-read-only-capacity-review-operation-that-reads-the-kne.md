# Add a read-only capacity-review operation that reads the knee signals and recommends raise, hold or lower for the dispatch budget

Nothing tells the operator when the worker budget should move; the knee is read by hand at each orchestrator check. Add a read-only `capacity-review` operation that reads the sampler episodes, the heavy pool waiting count, CPU and RAM and the tracked budget, and returns ONE of `raise`, `hold`, `lower` with the numbers. It runs on the runner tick, shows in `/wip`, and reaches the operator queue only when it recommends a change. It never edits the config. Needs card 3807.

## Background

Nothing tells the operator when the worker budget should move. Today the knee is read by hand: the orchestrator runs the `status` command of we:scripts/readiness/heavy-admission.mjs and the `lane-load` command of we:scripts/operations/host-sampler.mjs at each check, judges the numbers in its head, and logs a step in local notes; the schedule is a session-only cron. Operator, 2026-09-21: "keep adjusting as we learn. Suggest adjustment regularly, create a process that survives handoff". Add a READ-ONLY declared operation, `capacity-review`, that reads the sampler telemetry (we:scripts/operations/host-sampler.mjs: heavy-run episodes with admission_wait_s and wall_s per command family, host CPU and available RAM, live workers per kind), the heavy pool status (we:scripts/readiness/heavy-admission.mjs: waiting count and age), the live weighted load and the tracked `dispatch-budget` config, and returns the KNEE SIGNALS with ONE recommendation `raise`, `hold` or `lower` and the numbers behind it. It never edits the config; a change stays a reviewed commit. It runs on the runner tick (we:skills-src/conveyor/runner.mjs), not a session cron. Its last result shows in the `/wip` report (we:scripts/operations/wip-report.mjs) as one line, and reaches the operator queue only when it recommends a change. Method note: it replaces the p90 load1-versus-cores method of `suggestLimits` in we:scripts/operations/load-review.mjs (card #3737) with the direct signals of rule v4. Needs the tracked config of card 3807 (the budget it compares against). Design-first; not cleared for the conveyor.

## FOUND (2026-09-21, read in code on the prototype branch)

- **The signals are already recorded.** The sampler writes one `heavy.run.episode` per heavy command run (fields `family`, `wall_s`, `admission_wait_s`, `admitted`, `conc_start`, `conc_peak`, `calibration`), plus `host.cpu.busy_pct`, `host.mem.available_bytes` and live workers per kind (`we:scripts/operations/host-sampler-episodes.mjs`, `we:scripts/operations/host-sampler.mjs`). The `status` command of `we:scripts/readiness/heavy-admission.mjs` returns `waiting` (live waiters, each with `requestedAt`) and `staleWaiting` separately, so the waiting count and its age can be read without the stale-marker inflation.
- **Nothing computes the knee.** `we:scripts/operations/host-sampler.mjs` has `pressure` (a smoothed CPU brake), `lane-load` (a per-concurrency model) and `calibrate`; none returns "raise, hold or lower". `we:scripts/operations/load-review.mjs` has `suggestLimits` and `resourceReviewOwed`, but its method is p90 load1 against the core count with a 7-day cadence (card #3737), which is not the method the operator ruled in rule v4 (direct signals, ramp one step at a time, hold a few hours).
- **The exclusion mechanism does not exist.** Rule v4 says non-representative hours (the operator's photo dedupe, a runaway `fseventsd`) are tagged and excluded from step decisions. A search of the sampler files finds no annotation reader; the orchestrator's notes list it as a TO DO (`annotations.jsonl` with from, to, reason, exclude).
- **Rule v4 names the signals but gives no numbers.** It says stop where heavy-pool waiting starts to climb, watch gate duration against baseline, and hold if instantaneous CPU busy is above 95 for two readings in a row or available RAM is under 8 GB. It sets no gate-duration ratio, no hold window in hours ("a few hours") and no rule for when the budget was never used.

## DESIGN TO SETTLE (recommendations first; all thresholds provisional)

1. **Output.** `signals` (heavy-pool waiting count and oldest age; gate duration per family against baseline; CPU busy and available RAM against the emergency floor from the `dispatch-budget` config of card 3807; excluded windows with their reasons; coverage of the review window), the current `budget` and live weighted load, and ONE `recommendation` of `raise`, `hold` or `lower` with `reason` and, for a change, the next ramp value. "Not enough data" is a `hold` with reason `insufficient`, never a fourth verdict.
2. **Rules (proposal).** `lower`: any emergency-floor breach in the window, or heavy-pool waiting present at most readings together with gate duration over baseline. `raise`: the last change is older than the hold window (proposal 4 hours), every signal clean for that whole window, AND the live weighted load reached at least 80 percent of the budget at some point (a budget that was never used proves nothing), and it moves exactly one ramp step. `hold`: everything else. Numbers live in the config's `knee` block, not in the operation.
3. **Baseline for gate duration (proposal).** The median `wall_s` per command family of runs that had no concurrent heavy run (`conc_peak` of 1), taking calibration episodes as the reference when present, and at least 5 runs (the sampler's own `LANE_LOAD.minN`). Open: a `verify-lane` run varies with the size of the change; check the spread before trusting a ratio.
4. **Exclusions.** Minimal reader for a host-local `annotations.jsonl` (from, to, reason, exclude) next to the sampler telemetry, plus a one-line command to add one. Host-local, not tracked: a photo dedupe is a fact about one machine. Every excluded window is listed in the result. If exclusions cover more than half the review window the verdict is `hold: insufficient`.
5. **Read-only means compute-only.** Like `we:scripts/operations/gate-health.mjs`, every step is `compute`, so the HTTP surface derives as GET-only with no run record and the operation cannot reach a writer. A runner pass (the shape of the watches in `we:scripts/conveyor/`, wired from `we:skills-src/conveyor/runner.mjs`) calls it on the tick and stores the last result; the operation itself never writes. Recommend this over a scheduled cron, which lives in one session.
6. **Where it shows.** One line in `/wip` (`we:scripts/operations/wip-report.mjs`): `capacity: budget 8, live 3.75, signals clean, hold`. It reaches the operator queue (`we:scripts/operations/operator-queue.mjs`, through the `we:scripts/operations/wip-report-queue.mjs` Attention rules) only when the recommendation is `raise` or `lower`, so a quiet system adds nothing.
7. **Authority.** It suggests; the operator applies by a reviewed commit to the config. Same authority rule as #3737. It never edits the config, and a test asserts its static import graph reaches no writer.
8. **Not in this card.** Enforcing the emergency floor at dispatch time (rule v4 makes it the pacing gate; today that is the orchestrator and, in code, the load gate proposed in #3720). This card only REPORTS a breach. Also not here: the per-hardware formula (#3800).
9. **Statute conflict to state.** `we:docs/agent/platform-decisions.md` says "No load-average gate". The floor is CPU busy and RAM, not load average, but the statute should say so (also design point 9 of card 3807).
10. **Where it is built.** The sampler and load-review live on the prototype branch (#3383), so this is a prototype-branch build; the card is filed on main only to be tracked.

## Done when

1. **Executable** — `npx vitest run we:scripts/operations/__tests__/capacity-review.test.mjs` fails before this lands and passes after, with one fixture telemetry file per verdict under `we:scripts/operations/__fixtures__/capacity-review/`: `raise` (clean for the window, load reached the budget, last change old), `hold-clean-unused` (clean but the load never reached 80 percent), `hold-recent-change` (clean but the last change is inside the hold window), `hold-insufficient` (exclusions cover more than half the window), `lower-cpu-floor` (two consecutive readings above 95), `lower-ram-floor` (available RAM under 8 GB), `lower-pool-waiting` (waiters at most readings and gate duration over baseline). Each asserts the verdict and the numbers behind it.
2. **Assertable** — a test walks the operation's static import graph and finds no writer and no `node:fs` write; running it twice on the same fixture returns the same result and leaves the config file byte-identical.
3. **Executable** — the runner pass, given a fixture with `raise`, writes the last result and the next `/wip` render contains the `capacity:` line; with `hold` the operator queue gains no entry, with `raise` it gains exactly one.
4. **Handoff** — the review window, the hold window and every threshold come from the config, so a new session reproduces the recommendation from the repo and the telemetry alone.

Not verified: the gate-duration spread (design point 3), the 80 percent and 4 hour proposals (no data behind them yet), and that the runner tick can host a new pass without a budget of its own.
