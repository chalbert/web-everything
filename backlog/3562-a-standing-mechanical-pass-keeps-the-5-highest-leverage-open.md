# A standing mechanical pass keeps the 5 highest-leverage open decisions always prepared and published on the Decision Board

Ranks open decisions by the SAME leverage heuristic next-backlog-item/readiness already compute (transitiveUnblocks*1000+directUnblocks, via suggest-next --tier=B), takes the top 5, and for any not yet preparedDate-stamped, dispatches the SAME prepare-decision lane-agent pipeline we:scripts/conveyor/tick-core.mjs already uses for queue-blocking decisions. Once prepared, publishes/refreshes the "prepared to decide" section of the shared **Decision Board** artifact through the #3277 operation with FULL fork content (options, tradeoffs, bold default, confidence) — no summary that forces opening another file to rule on it. The Board's other section (a permanent decided-history ledger) is `we:backlog/x7wehz2`'s job — see *Cross-reference*; the two items share one artifact, ratified 2026-09-07.

## Why

The operator's own requirement, verbatim intent: always keep the 5 most-leverage decisions prepared and published where a decider can act on them. The published surface must contain ALL the information needed to actually decide — including every fork in full (options, tradeoffs, bold recommended default, confidence) — not a summary that requires opening another file to actually rule on it. That is a standing invariant ("always"), not a one-time batch — hence a mechanical pass, not another skill a session has to remember to run. **Naming note:** the surface was first scoped as a "decision docket" (pending decisions only); once `x7wehz2` added a permanent ledger of already-ratified decisions sharing the same artifact, "docket" no longer covered both halves, so the artifact itself is named the **Decision Board** — "docket" still names this item's own half (the pending-decisions ranking + prep-dispatch this item builds), "Board" names the published artifact both items write to.

## What already exists — reused, not reinvented (per this session's own newly-stated discipline: verify before filing)

- **Leverage ranking — one heuristic, already computed, already exposed as a callable operation.** `we:src/_data/backlog.js:609-653` derives `item.leverageScore = item.transitiveUnblocks * 1000 + item.directUnblocks` for every item (pure, deterministic, no body parsing). `we:scripts/readiness/engine.mjs:138-217`'s `computeSelection` ranks Tier-B (decision) items by `rankB` — prepared-first, then leverage desc, then size, then `NNN` — the exact rule `we:.claude/skills/next-backlog-item/SKILL.md` step 0b (`decision`/`review` invocation) cites as "rank by downstream-unblock leverage… most dependents wins." That ranking is already exposed as a callable, scriptable operation: `node we:scripts/operations/run.mjs suggest-next --tier=B --limit=5 --json` (`we:scripts/operations/suggest-next.mjs:247`'s `rankShortlist`). **Verified live during this item's research**: it returns exactly the top-5 ranked decisions with `leverageScore`, `prepared`, `preparedDate`, `transitiveUnblocks`, etc. — nothing to reinvent; this item's ranking step is a straight call to it (or its underlying pure `computeSelection`/`rankShortlist`, called in-process).
- **The prepare-dispatch pipeline already exists and is already mechanical — for a different population.** `we:scripts/conveyor/tick-core.mjs:391-429`'s `planPrepareSpawns` already spawns ONE `prepare-decision` lane agent per un-prepared decision in whatever `decisions` array it's handed, gated by `we:scripts/conveyor/tick-core.mjs:366-389`'s `retirePrepareGuards` (idempotent: a live guard entry or an open PR for the num suppresses a re-dispatch). The spawn itself runs through `we:scripts/operations/dispatch-lane.mjs:152`'s `LAUNCH_KINDS` (`'prepare-decision'` is already one of the five), briefed via `we:.claude/skills/conveyor/prepare-decision-agent-brief.md` — i.e. the SAME autonomous research-and-author pipeline `we:.claude/skills/prepare-decision-item/SKILL.md` documents for a human-run `/prepare`, already wired to run unattended. **This closes the second-blocker question up front: there is no missing "declare a prepare operation" gap to file — `dispatchLane({kind:'prepare-decision'})` is live, tested, and already used in production today.** What's missing is only the INPUT: today `we:scripts/readiness/dispatch-plan.mjs:299-308,590`'s `deriveDecisions(buildQueue, clearedNums)` populates `state.decisions` with decisions that are directly BLOCKING a queued build item — a reactive, queue-shaped population — never a standing "top 5 by leverage across the whole open backlog" window. A high-leverage decision that isn't currently blocking anything queued gets no mechanical push today. That's the actual gap this item closes.
- **The hand-run `/prepare all` pathway is real but is not a standing monitor.** `we:.claude/skills/prepare-decision-item/SKILL.md` step 1–2 already ranks the un-prepared Tier-B pool by this same leverage rule and lets a session iterate it one "go" at a time. `we:backlog/2451-prepare-candidate-set-must-be-origin-fresh-and-defer-aware.md` — read in full — is a **hardening fix** on that flow (origin-freshness for candidate bodies + operator-defer screening in `we:scripts/readiness/engine.mjs`'s `isFiller` gap and the skill's step 1), not itself a ranking or batch mechanism; it does not introduce or change any "always-5" guarantee. Both this skill and the queue-triggered dispatch above require *something* to invoke them (a session, or a queued build); neither runs standing watch over "are the top 5 currently prepared." This item is that missing always-on guarantee.
- **#3277 — confirmed still the right, still-unbuilt rendering foundation.** Re-read `we:backlog/3277-declare-an-operation-that-publishes-and-refreshes-a-decision.md` in full: its own scope is exactly "publish[ing] and refreshes a decision or architecture artifact… updating it in place when the decision moves" — the Decision Board is squarely that job, not a second publish mechanism. Confirmed unbuilt: its `## Done when` is still the unfilled scaffold TODO, and `git log --all` / branch search for `3277` turns up only the JIT-numbering commit that assigned it the number at land — no PR, no branch, no started work.

## What this item proposes

1. **A new standing mechanical pass — `we:scripts/conveyor/decision-docket-watch.mjs`** — built to the SAME structural template as `we:scripts/conveyor/duplicate-pr-watch.mjs` and `we:scripts/conveyor/parked-pr-conflict-watch.mjs`: pure-core / IO-shell split, wired into `we:skills-src/conveyor/runner.mjs`'s `makeCliMechanicalPasses` beside those two (the established "piggyback on a pass the headless runner already ticks" shape — no new cron/daemon). Each tick:
   - **(a) Rank.** Read the top 5 via `node we:scripts/operations/run.mjs suggest-next --tier=B --limit=5 --json` (or its in-process pure core). Obvious, not a fork: this is the identical heuristic `/next decision` already uses, already callable.
   - **(b) Dispatch prep for the un-prepared.** For any of the 5 with `prepared !== true`, dispatch through the EXACT SAME primitives `we:scripts/conveyor/tick-core.mjs`'s `planPrepareSpawns`/`retirePrepareGuards` already use — reusing those functions directly (they are already generic over any `decisions` array; they don't care whether the array came from a queue-blocker read or a leverage-window read) rather than re-implementing dispatch/guard/retirement a second time. Obvious, not a fork: the alternative (a parallel hand-rolled dispatch+guard mechanism) would duplicate exactly the machinery this item's own grounding shows already works.
   - **(c) Publish/refresh the Decision Board's "prepared to decide" section.** Once all 5 carry `preparedDate`, call #3277's publish/refresh operation (once #3277 lands) to render/update that section of the shared Decision Board artifact — the same artifact `x7wehz2`'s "decided history" ledger section writes into (ratified shape, see *Cross-reference*).
2. **The "prepared to decide" section renders FULL fork content for all 5** — every `## Fork N`'s options, tradeoffs, bold default, and `Skeptic:`/confidence note, verbatim from each decision's prepared body (`we:docs/agent/backlog-workflow.md`'s "prepared-fork shape" already IS this content; the Board renders it, it does not re-summarize it). No lead-paragraph/digest-only view — a decider must be able to rule from the Board alone, per the operator's own stated requirement above.
3. `blockedBy: ["3277"]` is the only cross-item blocker needed. As shown above, the dispatch half (1a/1b) needs nothing new that isn't already live; only the render half (1c) needs #3277.
4. **This pass is ACTION, not detect-only — unlike its two structural templates, and deliberately so.** `we:scripts/conveyor/duplicate-pr-watch.mjs` and `we:scripts/conveyor/parked-pr-conflict-watch.mjs` are alert-only by design (their own docstrings cite the "alert, don't auto-resolve content decisions" doctrine) because picking a winning PR or resolving a merge conflict is a content judgment a script cannot safely make. Triggering prep is a different kind of step: it is not a judgment call about which decision wins, only a trigger for the SAME autonomous research-and-author pipeline (1b above) that `we:scripts/conveyor/tick-core.mjs` already runs unattended today for queue-blocking decisions, with the SAME idempotency guard against double-dispatch. So step (b) is a real, unconditional auto-dispatch on every tick a top-5 item is found unprepared — never a mere report that a gap exists. (The `--dry-run` report mode in "Done when" #1 is a smoke/debug affordance, not the pass's normal behavior.)
5. **The target count (5) and the pass's own on/off switch are config, never hardcoded constants** — reusing this repo's existing conveyor tunable convention rather than inventing a new one:
   - **Count.** An exported `DEFAULT_DECISION_DOCKET_TARGET_COUNT = 5` (mirroring `we:scripts/conveyor/tick-core.mjs:145-157`'s `DEFAULT_BUILD_TTL_TICKS`/`DEFAULT_PREPARE_TTL_TICKS`/etc. — an exported default, overridable by the caller/env, never a bare literal inline), overridable via `process.env.WE_DECISION_DOCKET_TARGET_COUNT` (mirroring `we:scripts/conveyor/branch-drift.mjs:124`'s `process.env[MAX_BEHIND_ENV]` override-an-exported-default pattern). Passed through to `suggest-next --tier=B --limit=<N>`.
   - **Enable/disable.** A presence-checked boolean-flag env var, `WE_DECISION_DOCKET_WATCH_DISABLED` — mirroring `we:scripts/conveyor/queue.mjs:63`'s `CONVEYOR_NO_KIND_CHECK` / `:93`'s `CONVEYOR_NO_READY_CHECK` convention (an env var whose mere presence short-circuits the behavior to a no-op). Checked first thing in the pass's own entrypoint, so it degrades to a no-op tick rather than needing a change to `we:skills-src/conveyor/runner.mjs`'s `makeCliMechanicalPasses` — that function has no existing per-pass conditional-inclusion mechanism (every other wired pass runs unconditionally), so adding one there would be a second, larger change; a self-contained env check inside this pass's own entrypoint is the same shape already used for kill-switches in this codebase (`CONVEYOR_NO_KIND_CHECK` et al.) and needs no change to shared runner code.
   Both are obvious, not forks: the naming/placement follows directly from the two cited precedents; there is no genuine alternative worth weighing.

## Docket-shape fork — RATIFIED 2026-09-07 (operator), superseding this item's own earlier recommendation

This item originally flagged an open fork — "one page with 5 sections, or 5 separate linked artifact pages from one index?" — and recommended the 5-linked-pages shape (b). Once `x7wehz2` (the sibling ledger item, see *Cross-reference*) surfaced its own overlapping fork ("same artifact as this item's docket, two sections, vs. a separate page" — recommending "same artifact"), the operator ratified the combined shape across both items:

**One shared Artifact — the Decision Board — with exactly two top-level sections:**
1. **"Prepared to decide"** — this item's 5 highest-leverage pending decisions, each rendered as its own sub-section with FULL fork content (options, tradeoffs, bold default, confidence). Owned/refreshed by this item's mechanical pass.
2. **"Decided history"** — `x7wehz2`'s permanent, append-only, db-capability-backed ledger of ratified rulings. Owned/written by that item's page-side ruling actions.

This ratification **supersedes** this item's own earlier (b) recommendation: the 5 pending decisions render as sub-sections of ONE "prepared to decide" section (this item's original shape (a)), not as 5 separately-linked pages — a single shared artifact with 5 independent linked pages for the pending half plus a 6th for the ledger would not compose as "one shared Artifact, two sections." The refresh-churn concern that motivated the original (b) recommendation (a single re-publish rewriting the whole page on every one-of-five change) still applies and is now `#3277`'s own operation's problem to solve efficiently (e.g. section- or sub-section-scoped diffing), not a reason to fragment the artifact.
