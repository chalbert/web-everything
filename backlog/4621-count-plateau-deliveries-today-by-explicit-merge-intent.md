## Design

Contract ownership follows we:docs/agent/platform-decisions.md:143 (`#constellation-placement`); product computation stays in Plateau. The delivery semantics below implement the requested design at we:docs/agent/plateau-progress-view.md:100–110 and :136–142.

1. **Additive contract first.** Preserve the existing drain-only `deliveries` representation and old examples. Specify a separate optional schema-2 confirmed-delivery section with repo/PR identity, actual `mergedAt`, nullable merge SHA, full description, card references, kind, evidence and separate origin/executor attribution; include totals, included counts, source freshness, coverage intervals, cursor/reconciliation provenance and hourly/daily buckets. Absent extension means unknown to upgraded consumers. Existing schema-2 consumers can ignore it under the additive envelope (we:contracts/plateau-progress-view.schema.json:1499–1500). Do not rewrite the old drain tally as globally complete. Deploy accepting relay/client before the publishing adapter, retaining schema-1 compatibility supplied by #4620.
2. **One confirmed PR, one delivery.** Deduplicate by canonical full repo slug plus PR number across sources and restarts. Receipt time is observation time, never merge time; head SHA is not merge SHA. Missing repo or actual merge time excludes a row from exact calendar totals, with explicit partial coverage. Preserve raw evidence immutably; later authoritative classification can re-bucket that same record without changing the union size. Conflicting merge facts remain uncertain until reconciled. Never infer deliveries from resolved cards or completed sessions.
3. **Explicit classification.** Apply prevention metadata, then card-only plan/preparation evidence, then delivered builder build, then tool/runtime fix, otherwise other/unclassified. Mixed card/code requires explicit delivery kind; author/title alone is insufficient. Keep origin independent, so a builder-produced tool fix counts once as builder build. Preserve unknown raw kind codes and ambiguous historical records, following we:docs/agent/plateau-progress-view.md:140.
4. **Durable local history.** Proposed Plateau history adapter stores normalized records, evidence and per-source cursor/coverage together, atomically and idempotently, at an owner-resolved persistent location. Retain at least eight Toronto calendar days; on restart restore both records and coverage. Corrupt/missing/truncated state or cursor gaps produce collecting-history/partial, not zero. Do not use the relay's latest snapshot as the history database (we:docs/agent/plateau-progress-view.md:130).
5. **Comparable windows.** Today starts at America/Toronto midnight; half-open windows prevent boundary double counts. Show seven local-day buckets including today's partial day, plus adjacent trailing 60-minute windows. Compare only equal repo scope with complete coverage throughout both windows; gaps, newly added repos and missing baselines invalidate comparison. Preserve valid complete-zero observations distinctly from unknown (we:docs/agent/plateau-progress-view.md:102, :142).
6. **Existing read path only.** Integrate once per publisher cycle, preserving the 120-second baseline, source ages, authentication and transport described at we:docs/agent/plateau-progress-view.md:22. No browser or collector GitHub backfill. Show total and five mutually exclusive kind buckets, latest three full descriptions and access to remaining included records, truncation/coverage labels, hourly comparison and seven-day counts. Wrap text fully; system failures stay flow state (we:docs/agent/plateau-progress-view.md:61–63).
