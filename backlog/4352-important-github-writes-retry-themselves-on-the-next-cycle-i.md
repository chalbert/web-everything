# Important GitHub writes retry themselves on the next cycle, idempotently

A handful of daemon-posted GitHub writes (the CI-heal counter comments, review-status label writes) can be silently dropped by a shared GraphQL budget block, with nothing that retries them — live 2026-09-27 22:15-22:20Z `ci-heal-2821`'s comment was dropped this exact way (see #4309's evidence). Give each of the FEW writes that matter its own tiny "record it owed, retry on the caller's own next cycle" mechanism, guarded by the marker it already checks so it never double-posts — no shared queue, no cross-process replay daemon. This is the narrower design #4309's dropped write-queue/exactly-once-replay attempt (see its "Superseded design" section) was trying to solve the hard, general way; this card solves the SPECIFIC, small case instead.

## Why "next cycle" already exists — CORRECTED after Codex review (folded 2026-09-28)

**The first draft of this card mis-stated where the reliable cycle actually is — corrected here, not papered over.** `we:scripts/conveyor/ci-heal-mark.mjs` is NOT itself invoked every reconcile tick: it is invoked by the DISPATCHED HEAL AGENT, per `we:skills-src/conveyor/fix-agent-ci-brief.md` (line 310), AFTER that agent pushes a repair — a one-shot action inside one agent run, not a per-tick call. The actual per-tick function is `we:scripts/operations/ci-heal-pr-dispatch.mjs#runReconcileCiHealDispatch` (note the corrected path — `we:scripts/operations`, not `we:scripts/conveyor`), which DOES run every reconcile tick for every repo (confirmed by reading it: it re-derives `reconciled = reconcile(...)` fresh on every call and filters `ciHealEntries` from that live plan), but it only DISPATCHES A NEW AGENT for a PR still `ci:failed` under `ciHealCap` — it does not itself post the marker comment, and if CI recovers (or the cap is hit) before another agent is dispatched, NO further invocation of `we:scripts/conveyor/ci-heal-mark.mjs` for that PR will ever happen. **This means the original design's "the next reconcile tick retries it" claim was false as written** — the reconcile TICK is reliable, but it does not, by itself, retry the WRITE. The fix below moves the retry hook into the tick function that genuinely IS reliable, instead of the reactive CLI that isn't.

- **`we:scripts/conveyor/ci-heal-mark.mjs`**'s own marker, `CI_HEAL_COMMENT_MARKER` (line 47), and its durable counter, `countCiHealComments` (line 61) — reused, not re-derived, for the retry-completion check (with a fix, below, for a real gap Codex also found: the counter cannot tell "already posted THIS owed attempt" from "posted a different, unrelated earlier heal").
- **`we:scripts/conveyor/ci-heal-escalation-mark.mjs`** — same shape, its own marker `CI_HEAL_ESCALATION_MARKER` (line 48), read back by `parseCiHealEscalations` (line 98), which — unlike the heal marker above — already matches by HEAD (`latestCiHealEscalationForHead`, line 129): a real precedent for the head-scoped fix this card gives the heal marker too.
- **`we:scripts/review-set-label.mjs`** does NOT reliably self-heal a dropped write, contrary to the first draft's claim — see the corrected design below for the real gap Codex found (`we:scripts/conveyor/reconcile-core.mjs`'s `already-reviewed-head` short-circuit).

## Design (decided) — REVISED after Codex review (folded 2026-09-28; see "What changed" below)

**Per-caller "owed" record, not a shared queue.** When `we:scripts/lib/gh-throttle.mjs` refuses a write from one of the two opted-in CI-heal CLIs (a `budget_blocked` or `budget_exhausted` outcome), the CALLER — not the throttle — writes a small local marker recording "I owed PR `<repo>#<n>` a `<kind>` comment as of `<headSha>`" to a per-caller, host-shared JSON state file (a sibling of the existing lock-root state files `we:scripts/lib/gh-throttle.mjs` already manages), keyed by `(repo, pr, kind)`. No lease, no claim, no replay daemon.

**The retry hook lives in `we:scripts/operations/ci-heal-pr-dispatch.mjs#runReconcileCiHealDispatch`, not in `we:scripts/conveyor/ci-heal-mark.mjs`'s own reactive invocation.** This is the corrected design (see "Why next cycle" above for the gap this fixes): at the TOP of `runReconcileCiHealDispatch`'s per-repo run — which genuinely does execute every reconcile tick, independent of any single PR's CI state — add one cheap step, BEFORE the existing per-entry dispatch loop: read the small owed-record file, filter to entries for this repo, and for each not-yet-expired one, attempt the write directly (an in-process call into the SAME post-comment logic `we:scripts/conveyor/ci-heal-mark.mjs`/`we:scripts/conveyor/ci-heal-escalation-mark.mjs` already use, not a re-spawned agent). This makes the retry trigger the tick FUNCTION ITSELF (confirmed reliable), never the CLI's own next reactive call (confirmed NOT reliable — CI can recover, or the cap can be hit, before another heal agent is ever dispatched again for that PR).

**Guarded by a HEAD-SCOPED marker — a real, small addition, not "reuse as-is."** Codex's review found the existing `CI_HEAL_COMMENT_MARKER`/`countCiHealComments` pair cannot tell "this exact owed attempt already landed" from "an OLDER, unrelated heal already posted its own marker comment" — the counter is a pure aggregate with no per-attempt or per-head identity. Fix: `we:scripts/conveyor/ci-heal-mark.mjs#buildCiHealComment` gains a second line carrying the head sha the comment is FOR (mirroring the precedent `we:scripts/conveyor/ci-heal-escalation-mark.mjs#latestCiHealEscalationForHead` already sets for the escalation marker) — additive only, the counter's existing first-line-only match for the cap is unaffected. The owed-flush's completion check then searches recent marker comments for one whose head-line matches the OWED head specifically, not "any marker comment ever" — this is the actual double-post defense, corrected from the first draft's too-loose "if a marker comment is already live" check.

**Bounded, not indefinite.** An owed record older than a small number of cycles (or a small wall-clock ceiling, matching the existing `ciHealCap` philosophy) is dropped and logged rather than retried forever — the same "never strand a caller behind an unbounded wait" discipline `we:scripts/lib/gh-throttle.mjs`'s own fail-open gates already follow elsewhere in that file.

**`we:scripts/review-set-label.mjs` has a REAL gap, not a self-healing one — corrected from the first draft.** Codex's review found: if the verdict comment posts but the label write is then refused, `we:scripts/conveyor/reconcile-core.mjs`'s `already-reviewed-head` short-circuit (line 1069) sees the comment's `reviewed-sha` marker already matches the live head and concludes review is DONE for that head — so it never schedules another review-set-label run, and the label write is stuck, not retried, contrary to the first draft's "it already retries unconditionally" claim. Fix, scoped to the actual short-circuit rather than a new owed-record mechanism: `we:scripts/conveyor/reconcile-core.mjs`'s `already-reviewed-head` check gains a second condition — the live label set must ALSO match the verdict the comment recorded, not just the head sha — before it short-circuits. A head whose comment matches but whose label doesn't is treated as needing a fresh review-set-label run, reusing reconcile's own existing re-run machinery (no new retry mechanism for this file at all; the fix is making an over-trusting short-circuit check what it claims to check).

**`we:scripts/conveyor/advisory-fix-mark.mjs` is explicitly OUT of scope**, same reasoning #4309's dropped design already worked out and this card inherits: its marker is not a pure counter (a later marker can retroactively "address" an earlier finding), so retry-on-next-cycle for it needs its own episode-id design, not this shape. Not touched here.

**What changed from the first draft (Codex review, round 1, folded 2026-09-28):** (1) the retry trigger moved from "`we:scripts/conveyor/ci-heal-mark.mjs`'s own next invocation" (not actually reliable) to "`runReconcileCiHealDispatch`'s per-tick owed-flush" (confirmed reliable); (2) the heal marker gained a head-scoped line so the completion check can't be fooled by an older, unrelated heal comment; (3) `we:scripts/review-set-label.mjs`'s fix moved from "no change needed, just confirm surfacing" to a real, small, scoped fix in `we:scripts/conveyor/reconcile-core.mjs`'s own short-circuit — the actual root cause of that file's stuck-label gap.

## Risks

- **A "succeeded server-side but client saw a failure" race.** `gh`'s own timeout/network-blip failure modes can make a write look refused when it actually landed. Mitigated by the head-scoped marker check (corrected design, above): before retrying, re-read live comments for one whose head-line matches the owed head, and skip if found. No op-id, no exactly-once machinery beyond that — the head-scoped marker line IS the caller's own durable dedupe key.
- **An owed record surviving past its usefulness** (the PR merges or closes before the retry runs). Corrected from the first draft: the owed-flush now runs UNCONDITIONALLY every tick (not gated on the PR still being `ci:failed`, per the corrected design above), so it can no longer rely on "reconcile stops planning ci-heal for this PR" to prune stale work. Fix: the flush step itself does one cheap live-state check (PR merged/closed) for each owed entry before retrying, dropping and logging a merged/closed PR's owed write as moot rather than posting a heal comment to a PR nobody will see it on; anything still open is retried regardless of current CI color (posting a slightly-late heal comment to a PR that has since gone green is harmless — it is still an accurate historical record of the attempt).
- **Scope creep back toward the dropped design.** This card is deliberately NOT the write-queue: no shared lock-root queue file, no lease, no claim, no cross-process replay CLI, no op-id search across PR comment pages. If the owed-record mechanism grows any of those, that is a sign this card has drifted back into #4309's dropped shape and should stop and re-scope, not add more machinery.
- **Two callers, two owed-record files or one shared shape?** `we:scripts/conveyor/ci-heal-mark.mjs` and `we:scripts/conveyor/ci-heal-escalation-mark.mjs` have near-identical marker/counter shapes; sharing one small pure module for "read/write/prune an owed record" (not a "queue") between them avoids near-duplicate code without re-creating the shared-queue complexity — this is a size/implementation call for the build session, not a design fork.
- **The `already-reviewed-head` fix touches a shared short-circuit other logic may lean on.** `we:scripts/conveyor/reconcile-core.mjs`'s check is read by more than just the label-write gap this card fixes; tightening it (comment AND label must match, not just comment) must be checked against every existing caller of that short-circuit before landing, not assumed safe by inspection alone — named as the build session's own task, below, not resolved here.

On a budget refusal (`gh-throttle`'s budget-blocked/exhausted text, via `isRateLimitShaped`) both CLIs record the write owed and exit 0 with `owed:true`. `we:scripts/operations/ci-heal-pr-dispatch.mjs#runReconcileCiHealDispatch` flushes owed writes for its repo first, before the reconcile read: merged/closed → dropped as moot; head-matched marker already live → cleared; else posted. Bounded at 6h / 24 tries.
- Task 4 finding: tightening `already-reviewed-head` to "label must match" on its own would have removed the #2588 guard completely. On a first accept the comment posts before the label swap, and any `review:pending` head with an accept marker already has a mismatched label, so every such head would get re-dispatched. The tightening is gated on time instead: `we:scripts/conveyor/reconcile-core.mjs#acceptLabelDropped` fires only for `review:pending` (never `review:human`) when the accept comment is older than `ACCEPT_LABEL_GRACE_MS` (15 min). The PR then falls through to the ordinary review dispatch with `relabelOwed: true`. If there's no clock or no comment timestamp, it fails closed to the old refusal. All three `dispatchReviewRow` callers are covered (the OWED table, owed-ci-rerun parallel, not-a-ci-break parallel).
