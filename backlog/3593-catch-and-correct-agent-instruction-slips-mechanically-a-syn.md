# Catch and correct agent instruction-slips mechanically - a syntactic scanner plus a standing supervisor

Across one live session (2026-09-04), dozens of subagents were caught mid-turn doing three distinct things: (a) falsely claiming a background wait was being tracked (e.g. an "I've set up a monitor" claim with no actual Monitor tool_use anywhere in the transcript window) or ending a turn passively assuming a plain backgrounded shell command would wake them; (b) hand-spawning a bespoke claude -p/claude --bg session instead of using a declared operation such as we:scripts/operations/review-dispatch.mjs; (c) conflating "the tracking card landed" with "the capability is actually built." All three were caught only because the operator manually read each subagent's transcript with we:skills-src/inspect-agent-health/agent-health.mjs one at a time and sent a corrective SendMessage. This does not scale and depends entirely on a human noticing by chance.

The agreed split, stated explicitly per the operator's own framing (the design frame this epic is staged around): (1) THE SYNTACTICALLY-CHECKABLE HALF - a false "waiting on a monitor" claim with no real Monitor tool_use in the recent transcript window, or a Bash command matching a raw claude -p/claude --bg spawn outside a declared operations script - these are regex/pattern-detectable against a transcript, not judgment calls. (2) THE JUDGMENT HALF - whether a hand-composed prompt should have used an existing declared operation instead, or whether an action was redundant because a mechanical pass already handles it - these need real reasoning, not a scanner. The two stages below are complementary, not sequential-blocking: a standing supervisor (stage 2) can consume the syntactic scanner's (stage 1) output once both exist, but each has independent value on its own.

Checked before filing, per this repo's own capability-search doctrine (we:backlog/3559-search-operations-skills-and-the-backlog-before-proposing-or.md, status: resolved, shipped as we:scripts/capability-search.mjs):

- we:skills-src/inspect-agent-health/agent-health.mjs - read in full. It is a single-target, on-demand, bounded-read tool: given one agent id/transcript, it tails the last N JSONL entries and classifies ACTIVE / BLOCKED_ON_CHILD / BLOCKED_ON_TOOL / IDLE_OR_STALLED, where BLOCKED_ON_CHILD specifically detects a pending tool_use with no matching tool_result (especially a nested blocking Agent() call). It does NOT detect the false-monitor-claim pattern this epic is about: there is no cross-check anywhere in it between an agent's own prose claim (e.g. "I've set up a monitor") and whether a real Monitor tool_use actually appears in its transcript - every verdict is built entirely from tool_use/tool_result pairing plus idle time, never from text-claim matching. It is also strictly single-agent per invocation, with no fleet-wide enumeration of its own. It is the right primitive to extend (the bounded-read safety property, the transcript-location logic), not to replace.
- A standing supervisor pattern already exists in this repo, but for a different target: we:skills-src/conveyor/supervisor.mjs is a resident restart/backoff/alerting wrapper around the conveyor tick RUNNER process itself (spawn the child, classify its exit, back off on repeated crashes, desktop-notify on a crash-loop-at-ceiling or an idle-with-queue condition) - it says nothing about an individual dispatched subagent's own claims or behavior. Relevant prior art for the persistent-process shape the decision below weighs, but not a pre-existing answer to this epic's actual problem.
- The filesystem-based fleet-enumeration mechanism this epic's first slice needs already has a working precedent in this repo: we:scripts/dev/active-progress-watch.mjs already walks ~/.claude/projects/<project-slug>/**/subagents/*.jsonl (and the workflow-nested subagents/workflows/<runId>/ shape) directly off disk, with no ListAgents tool involved, deriving the project slug from cwd and freshness from file mtime, to build its own live-progress feed. The scanner filed below should reuse this exact enumeration convention rather than re-deriving it.
- Adjacent prior art, cross-referenced both ways: we:backlog/2833-subagent-stall-reaping-detect-a-subagent-blocked-on-a-backgr.md shipped a delivery-path PREVENTION for a related but distinct failure mode (a genuinely-stalled subagent blocked on a background wait) via a synchronous-verify wrapper plus a PreToolUse guard, and explicitly deferred the harness-level "detect and auto-reap/resume a stuck subagent" half to we:backlog/2881-subagent-stall-harness-backstop-detect-auto-clear-a-stuck-ba.md (still status: open), on the judgment that it "leans on agent-runtime capability largely out of in-repo scope." This epic's syntactic pattern (a false CLAIM in the transcript text, independent of whether the agent is actually stalled) is a different failure mode from a genuine stall, so this is not a duplicate - but #2881's own scoping judgment is directly relevant evidence for this epic's open decision below about how a supervisor can actually be invoked.
- Checked we:scripts/guard-bash.mjs (the PreToolUse(Bash) guard already live for other footguns, e.g. it already blocks a backgrounded verify-lane run): it has no existing pattern match for a raw claude -p/claude --bg spawn today, confirmed by grep - this really is unbuilt, not a rediscovery.

Staged as: Stage 1 (this epic's first buildable slice, filed as its own story) - a report-only syntactic scanner extending we:skills-src/inspect-agent-health/agent-health.mjs's bounded-read approach across every currently-active subagent transcript, detecting false monitor-wait claims specifically (pattern (a) above, the clearest and most common catch from the session that motivated this). Stage 2 - a standing supervisor that can consume Stage 1's output and exercise judgment on the redundant/bespoke-prompt cases (patterns (b) and (c)) - NOT assumed to be a simple scanner extension; the decision filed below decides its actual operating shape. Stage 3 (not detailed here, out of scope until Stage 1/2 show it is needed) - auto-correction, once the report-only stage has a track record of real catches.
